# User Spec: Доступ к панели по заявке с одобрением администратором

## What we're building

Доступ к рабочей панели сервиса выдаётся не автоматически после входа через Яндекс, а только
после того, как администратор одобрил заявку пользователя. Сразу после авторизации пользователь
без доступа видит плашку с кнопкой «Запросить доступ» и контактным email. Два выделенных
аккаунта-администратора получают письмо о новой заявке и видят в панели список всех
пользователей с галочкой «есть доступ к сервису», которую могут ставить и снимать.

Проверка выполняется на сервере: без выданного доступа закрыт не только интерфейс, но и API
с расчётами, чатами и настройками.

## Why

Сейчас панель открыта любому, кто вошёл через Яндекс OAuth. Продукт находится в стадии
контролируемого доступа: нужно вручную решать, кто пользуется сервисом, и уметь отзывать
доступ у конкретного пользователя, не отключая авторизацию целиком.

Кроме того, API с данными расчётов сегодня не проверяет авторизацию вовсе — идентификатор
пользователя берётся из адреса запроса. Пока это так, отзыв доступа остаётся декоративным.

## How it should work

1. Пользователь входит через Яндекс OAuth и попадает на `/panel`.
2. Система проверяет, выдан ли ему доступ.
3. Если доступ не выдан — вместо рабочего интерфейса панели показывается плашка:
   объяснение, кнопка «Запросить доступ» и контактный email для связи.
4. Пользователь нажимает «Запросить доступ» — создаётся заявка.
5. Кнопка становится неактивной, плашка сообщает «Заявка отправлена, ожидайте решения».
   Повторно подать заявку, пока текущая на рассмотрении, нельзя.
6. На почту администраторов уходит письмо о новой заявке с логином и email заявителя.
7. Администратор входит в панель и видит дополнительный раздел «Пользователи» —
   список всех аккаунтов с галочкой «есть доступ к сервису» напротив каждого.
8. Администратор ставит галочку — пользователь получает доступ; снимает — доступ отзывается.
9. Пользователь с выданным доступом при следующем открытии панели видит рабочий интерфейс.
10. Пользователь, у которого доступ отозвали, при следующем открытии панели снова видит плашку.
11. Обычный пользователь раздела «Пользователи» не видит и не может им пользоваться.

## Acceptance Criteria

- [ ] US-1: Авторизованный пользователь без доступа видит плашку запроса доступа вместо рабочего интерфейса панели
- [ ] US-2: Плашка содержит кнопку «Запросить доступ» и контактный email
- [ ] US-3: Нажатие кнопки создаёт заявку; повторная подача при заявке на рассмотрении невозможна
- [ ] US-4: После подачи заявки плашка отображает статус «на рассмотрении»
- [ ] US-5: При создании заявки администраторам уходит email-уведомление с логином и email заявителя *(выполняется во второй фазе — см. tech-spec → Implementation Tasks)*
- [ ] US-6: Ровно два выделенных аккаунта имеют права администратора
- [ ] US-7: Администратор видит в панели раздел со списком всех пользователей
- [ ] US-8: Напротив каждого пользователя есть галочка «есть доступ к сервису», отражающая текущее состояние
- [ ] US-9: Администратор может выдать доступ, поставив галочку
- [ ] US-10: Администратор может отозвать доступ, сняв галочку
- [ ] US-11: Пользователь с выданным доступом видит рабочий интерфейс панели
- [ ] US-12: Пользователь без прав администратора не видит раздел управления пользователями
- [ ] US-13: Неадминистратор не может выдать доступ никому, включая себя, обращаясь к API напрямую
- [ ] US-14: Администратор всегда имеет доступ к сервису, отдельная заявка ему не нужна
- [ ] US-15: Расчёты, чаты и настройки доступны через API только их владельцу и только при выданном доступе
- [ ] US-16: После отзыва доступа пользователь теряет и доступ к данным через API, а не только интерфейс
- [ ] US-17: Сессию нельзя получить, предъявив серверу готовый OAuth-токен в обход штатного входа

## Constraints

- Авторизация остаётся на Яндекс OAuth — своей регистрации и паролей не появляется.
- Список администраторов фиксируется в БД (колонка роли), конкретные логины будут
  указаны пользователем перед деплоем.
- Сбой отправки письма не должен ронять создание заявки — заявка важнее уведомления.
- Проверка доступа выполняется на сервере. Гейт только в интерфейсе не считается выполнением
  требований: данные расчётов лежат за API, и без серверной проверки отзыв доступа не работает.

## Risks

- **Риск:** администратор ошибочно снимает галочку у себя или у второго администратора и
  теряется управление доступом. **Mitigation:** роль администратора хранится отдельно от
  флага доступа; администратор всегда проходит проверку доступа независимо от флага.
- **Риск:** отправка письма через SMTP недоступна или медленная, пользователь видит ошибку
  при подаче заявки. **Mitigation:** письмо отправляется асинхронно, ошибка логируется,
  заявка создаётся в любом случае.
- **Риск:** пользователь спамит заявками. **Mitigation:** запрет повторной заявки при уже
  существующей на рассмотрении.
- **Риск:** SMTP-креды попадают в репозиторий. **Mitigation:** только переменные окружения
  и секреты CI, никаких значений в коде и compose-файлах.

## Technical Decisions

- Решили гейтить доступ по флагу у пользователя, а не по наличию одобренной заявки,
  потому что отзыв доступа должен работать независимо от истории заявок.
- Решили хранить роль администратора в БД отдельной колонкой, потому что список
  администраторов должен читаться вместе со списком пользователей.
- Решили отправлять письмо администраторам автоматически, потому что иначе заявка
  может пролежать незамеченной.
- Решили защищать на сервере новые эндпоинты (заявки и админские), потому что без этого
  любой пользователь смог бы выдать доступ сам себе и одобрение потеряло бы смысл.
- Решили в рамках этой же фичи закрыть существующие `/api/v1/users/*`, потому что иначе
  отзыв доступа не работает: данные остаются доступны напрямую, а таблица `users` — та же,
  где теперь хранятся роль и флаг доступа — пополняется анонимными записями.
- Решили удалить приём готового OAuth-токена (`POST /auth/yandex`), потому что после этой
  фичи из такой сессии выводится роль администратора, а штатный вход этот путь не использует.
- Решили добавить проверку источника запроса на изменяющих операциях и параметр `state`
  в OAuth-редирект, потому что обе точки правятся этой фичей и без них выдача доступа
  уязвима к запросу с чужого сайта.

## Testing

**Unit tests:** always done, not up for discussion.

**Integration tests:** да — проверка доступа и админских операций затрагивает БД и HTTP-слой,
логика распределена между middleware, сервисом и репозиторием.

**E2E tests:** нет — в проекте нет E2E-инфраструктуры, а сквозной сценарий покрывается
ручной проверкой в панели и интеграционными тестами API.

## How to Verify

### Agent verifies

| Step | Tool | Expected result |
|-----|-----------|-------------------|
| 1. Применить миграции на чистой БД | bash (`docker compose up`) | Миграции проходят, колонки роли и доступа созданы, таблица заявок создана |
| 2. Запросить список пользователей без куки | curl | 401 |
| 3. Запросить список пользователей под неадминистратором | curl | 403 |
| 4. Выдать доступ под неадминистратором | curl | 403, флаг доступа в БД не изменился |
| 5. Выдать доступ под администратором | curl | 204, флаг доступа в БД выставлен |
| 6. Отозвать доступ под администратором | curl | 204, флаг доступа в БД снят |
| 7. Создать заявку под пользователем без доступа | curl | 201, заявка появилась в БД |
| 8. Повторно создать заявку тем же пользователем | curl | 409 |
| 9. Открыть `/panel` пользователем без доступа | Playwright MCP | Отрисована плашка запроса доступа, рабочего интерфейса нет |
| 10. Открыть `/panel` администратором | Playwright MCP | Виден раздел со списком пользователей и галочками |
| 11. Открыть `/panel` пользователем с доступом, но без прав администратора | Playwright MCP | Раздела «Пользователи» в навигации нет |
| 12. Запросить чужие чаты с валидной сессией | curl | 403 или 404, чужие данные не возвращаются |
| 13. Запросить свои чаты после отзыва доступа | curl | 403, данные не возвращаются |
| 14. Отправить готовый OAuth-токен на `POST /auth/yandex` | curl | 404 — маршрут удалён |
| 15. Выдать доступ запросом с посторонним заголовком `Origin` | curl | Запрос отклонён, флаг не изменился |

### User verifies
- Письмо о новой заявке действительно приходит на почту администраторов — проверяется вручную,
  потому что доставка зависит от боевых SMTP-кредов и настроек почтового провайдера.
- Логины двух администраторов заданы верно — известны только пользователю.
