# Task 6: Перевод существующих маршрутов на личность из сессии

## Required Skills

Before executing the task, load:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Today `/api/v1/users/{userID}/*` takes the owner straight from the URL path segment
(`server/internal/handler/http.go:26-70`, `handleUsers`) with zero auth check. This means
Task 5's access revocation (`SetAccess(granted=false)`) has no effect on this surface — any
caller can still read and write any user's settings, chats, and calculations by putting a
different login in the URL. Ownership cannot be smuggled through the request body as a
fallback either: `CreateChatInput` (`server/internal/service/costing.go:164-166`) and
`OrderInput` (`:87`) carry no owner field, `UserID` is only present on the *output* types
`CalculationResult` (`:114`) and `Chat` (`:154`), and `decodeJSON`
(`server/internal/handler/http.go:226-239`) calls `decoder.DisallowUnknownFields()`, so an
extra `user_id` key in the body already returns 400 today. This is Decision 6 in the tech-spec.

This task removes the `{userID}` segment from every `/api/v1/users/*` route and takes the
owner from the request context populated by Task 4/5's `RequireAuth` + `RequireAccess`
middleware chain (wired onto this prefix per the Architecture routing table:
`RequireSameOrigin` → `RequireAuth` → `RequireAccess`). After the segment is gone, there is no
remaining channel — URL, body, or query — through which a caller can address another user's
data. This closes US-15 (data isolation) and US-16 (revocation actually takes effect).

`server/api/openapi.yaml` is updated to match: the five existing `/api/v1/users/{userID}/...`
paths lose the `{userID}` segment, and the four `/api/v1/access/*` + `/api/v1/admin/*` routes
introduced by Task 5 are documented. The file is already stale in other ways (pre-`003`-migration
settings shape, missing delete/restore chat routes) — fixing that pre-existing drift is out of
scope; only what this feature's route surface touches needs to be accurate.

## What to do

- In `server/internal/handler/http.go`, rewrite `handleUsers` (currently `path :=
  strings.TrimPrefix(r.URL.Path, "/api/v1/users/")`, `parts := splitPath(path)`, `userID :=
  parts[0]`, `resource := parts[1]`) so the owner login is no longer read from the URL. Take it
  instead from the request context populated by Task 4's `RequireAuth` (and confirmed present
  by `RequireAccess`, both wired onto `/api/v1/users/` per the Architecture routing table) —
  see `middleware.go` (created by Task 4) for the exact context accessor/identity type to call.
  Shift the manual path parsing down by one segment now that `userID` is gone: `resource :=
  parts[0]`, chat id (where present) moves to `parts[1]`, and the trailing action segment
  (`restore`/`calculate`/`calculations`) moves to `parts[2]`. Keep the same `switch` structure
  and the same `writeAPIError(w, http.StatusNotFound, "route not found")` fallback for
  unmatched shapes.
- Rewrite the five route shapes: `settings` (GET/POST), `chats` (GET/POST), `chats/{chatID}`
  (DELETE), `chats/{chatID}/restore` (POST), `chats/{chatID}/calculate` (POST),
  `chats/{chatID}/calculations` (GET), `market-feedback` (POST) — all without the leading
  `{userID}` segment. Each of the eight `handle*` methods (`handleUpsertSettings`,
  `handleGetSettings`, `handleCreateChat`, `handleListChats`, `handleDeleteChat`,
  `handleRestoreChat`, `handleCalculate`, `handleListChatCalculations`, `handleMarketFeedback`)
  keeps its existing `userID string` parameter and body — only the caller in `handleUsers`
  changes what it passes as that argument (context-derived login instead of `parts[0]`).
- Confirm `/api/v1/users/` is actually wired through `RequireSameOrigin` → `RequireAuth` →
  `RequireAccess` in whatever route-assembly Task 5 built (reused by its own tests, per the
  tech-spec's testing strategy). If that builder lives in `server/internal/handler/access.go`,
  extend it to also register `APIHandler.Register`'s mux under the same middleware chain; if it
  lives elsewhere (e.g. `main.go`), wire it there instead — the requirement is that
  `http_test.go` exercises the exact same assembled routes as production, not a
  reimplementation of the chain.
- Update `server/api/openapi.yaml`: rename the five existing `/api/v1/users/{userID}/...` paths
  by dropping the `{userID}` path parameter and its `parameters:` entry — `/settings`,
  `/chats`, `/chats/{chatID}/calculate`, `/chats/{chatID}/calculations`, `/market-feedback`
  become `/api/v1/users/settings`, `/api/v1/users/chats`,
  `/api/v1/users/chats/{chatID}/calculate`, `/api/v1/users/chats/{chatID}/calculations`,
  `/api/v1/users/market-feedback` (keep the `chatID` path parameter — that segment is
  untouched by this task). Add the four routes Task 5 introduced, using the request/response
  shapes from the tech-spec's Architecture → routing table: `GET /api/v1/access/me` → 200
  `{login, display_name, email, role, has_access, request_status, contact_email}` / 401; `POST
  /api/v1/access/requests` → 201 / 409 / 401 / 403; `GET /api/v1/admin/users` → 200
  `{items:[UserRecord]}` / 401 / 403; `POST /api/v1/admin/users/{login}/access` with body
  `{"granted": bool}` → 204 / 400 / 401 / 403 / 404. Do not otherwise touch the file's
  pre-existing staleness (the settings schema predates migration `003`, delete/restore chat
  routes are undocumented) — out of scope for this task.
- Write `server/internal/handler/http_test.go` as an integration test file using
  `net/http/httptest` against the same real route assembly used above (not a hand-built mux),
  covering every rewritten route per the TDD Anchor below.

## TDD Anchor

Tests to write BEFORE implementation. Write → run → confirm they fail → write code → confirm they pass.
All of these live in `server/internal/handler/http_test.go`, built on the shared route
assembly (see "What to do") and a stub session/identity resolver, not the real `auth.Store`.

- `TestHandleUsers_NoCookies_401` — `GET /api/v1/users/chats`, `GET /api/v1/users/settings`,
  `POST /api/v1/users/chats/{id}/calculate` without cookies → 401 on each
- `TestHandleUsers_NoAccess_403` — same three routes, session belongs to a user with
  `has_access=false` → 403 on each (US-16)
- `TestHandleUsers_WithAccess_200_OwnerScoped` — same three routes (plus `chats` POST/GET,
  `chats/{id}` DELETE, `/restore`, `/calculations`, `market-feedback`), session belongs to a
  user with `has_access=true` → 200/201/204 as appropriate, and returned data belongs to the
  session's own login, not any login supplied elsewhere in the request
- `TestHandleUsers_ForeignOwnerUnreachable` — with a valid session, no URL segment exists to
  target another owner's data; substituting a foreign login into the request body (e.g. an
  unknown `user_id` field) or into a query string parameter does not change which owner's data
  is returned or mutated (US-15) — assert via the response body/store state that only the
  session owner's data was touched
- `TestRegisterRoutes_LegacyUserIDSegment_NotFound` — a request shaped like the old
  `/api/v1/users/{login}/chats` (a stray extra path segment) no longer resolves to a chats
  route — either 404 (route not found) or, if some segment happens to parse as `chats`,
  behaves per this task's new contract, never using that segment as an owner override

## Details

**Files:**
- `server/internal/handler/http.go` — `handleUsers` (lines 26-70) currently does
  `userID := parts[0]; resource := parts[1]` and passes `userID` to all eight `handle*`
  methods. Remove the URL-based `userID` extraction, shift the remaining `parts` indices down
  by one for every route shape, and source the owner login from context instead. The eight
  `handle*` method signatures (`handleUpsertSettings` through `handleMarketFeedback`) do not
  need to change — only what `handleUsers` passes as their `userID`/first argument.
- `server/internal/handler/http_test.go` — does not exist yet; create it as the integration
  test file per the TDD Anchor, following the same `httptest`-based style Task 5 establishes in
  `access_test.go`/`middleware_test.go` (real route assembly, stub session/identity resolver
  rather than a live `auth.Store`, since `auth.Store` requires a real `*sql.DB`).
- `server/internal/handler/access.go` — inspect what Task 5 actually placed here. If the
  reusable route-building function (built so tests exercise the real `main.go` wiring) lives in
  this file, extend it to register `/api/v1/users/` under `RequireSameOrigin → RequireAuth →
  RequireAccess`. If Task 5 put that builder in `main.go` or a separate file instead, make the
  equivalent change there and leave `access.go` alone — do not force a change into this file if
  it isn't the right place.
- `server/api/openapi.yaml` — five `paths:` entries change (see "What to do" for the exact
  before/after route strings); four new `paths:` entries are added for the Task 5 surface.
  Reuse the existing `ErrorResponse`/`BadRequest`/`NotFound` components where response shapes
  match; add new response schemas only if the access/admin payloads don't fit the existing ones.

**Dependencies:** Task 4 (`middleware.go`'s `RequireAuth`/`RequireAccess` and the context
identity type/accessor) and Task 5 (the four `/api/v1/access/*` + `/api/v1/admin/*` routes,
`access.go`, and whatever route-assembly function Task 5 introduced for its own tests) must
both be implemented first — this task's `depends_on: [5]` covers both transitively.

**Edge cases:**
- A request with a stray extra path segment where `{userID}` used to be (e.g.
  `/api/v1/users/someone/chats`) must not resolve to the `chats` route or accidentally treat
  that segment as an owner override — it should fall through to the existing "route not found"
  404 default in the `switch`.
- `handleMarketFeedback`'s existing `h.deepseek == nil` branch (503) and `handleCalculate`'s
  DeepSeek-integration branch must keep working unchanged — only the owner-resolution step
  before them changes.
- `decodeJSON`'s `DisallowUnknownFields()` (line 230) already rejects a foreign `user_id` key
  in `CreateChatInput`/`OrderInput` bodies with 400 — this task doesn't need to add new
  filtering for that, just avoid re-introducing any owner field into those input structs.

**Implementation hints:** Task 4's middleware places the authenticated identity in the request
context; read the login from there via whatever accessor `middleware.go` exports (check that
file once Task 4 is done — do not guess a function name that doesn't match what Task 4 actually
built). `RequireAccess` running ahead of `handleUsers` guarantees a valid, access-checked
identity is always present in context by the time `handleUsers` executes, so no additional
nil/error handling is needed inside `handleUsers` itself for a missing identity.
