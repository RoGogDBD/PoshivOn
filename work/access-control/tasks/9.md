## Description

This is the deploy-configuration task that makes the rest of the feature actually reach
production and actually get tested before it ships. Three unrelated gaps close in this task,
all confined to CI/CD and infra files — no application code changes:

1. **`CONTACT_EMAIL` doesn't reach the container.** Task 5 (server) adds `CONTACT_EMAIL` to
   `config.go` as a var read via `envOrDefault("CONTACT_EMAIL", "")`, shown on the
   no-access banner (US-1..US-4). An env var only reaches `poshivon_app` on prod if it survives
   **five** hops: GitHub repo secret → `env:` block of the Deploy step
   (`.github/workflows/deploy.yml:93-120`) → the `envs:` comma-separated allowlist on the same
   step (`deploy.yml:126`) — a var present in `env:` but absent from `envs:` is silently
   dropped by `appleboy/ssh-action`, no error — → the `.env` heredoc written on the server
   (`deploy.yml:234-260`) → the `environment:` mapping in `docker-compose.prod.yml:5-26`. Miss
   any one hop and the banner falls back to the empty-string default with no error anywhere.

2. **`/auth/refresh` is not proxied on prod.** Both the heredoc-generated prod nginx config
   (`deploy.yml:130-233`) and `client/nginx.conf:13-67` proxy `/auth/status`, `/auth/me`,
   `/auth/logout`, `/auth/yandex`, `/auth/yandex/code` to `poshivon_app:8080`, but not
   `/auth/refresh`. That path falls through to `location /` → the SPA container →
   `try_files ... /index.html` → HTTP 200 with HTML. The client's `refreshAuthSession`
   (`client/src/utils/yandexAuth.js:18-25`) reads `response.ok`, which is `true` for that HTML
   200, so `authFetch` retries the original request with the same stale cookie and gets the
   same 401 again — the refresh-retry path is silently dead in prod. Separately, Task 4 deletes
   the backend route `POST /auth/yandex` (Decision 7, implicit OAuth branch removed), so its
   proxy entry in both configs is now dead weight pointing at a 404 and should be removed
   alongside adding `/auth/refresh`.

3. **No test workflow runs anywhere.** The only existing workflow, `deploy.yml`, triggers on
   `push: tags` and only builds/pushes images — nothing runs `go test ./...` before, during, or
   after. Tasks 1-8 add a real Go test suite, including DB-backed contract tests on
   `PostgresRepository` (`store_test.go` per Testing Strategy) that `t.Skip` when
   `TEST_DB_DSN` is unset — meaning today those tests would report `ok` in CI even though they
   never execute. This task adds `.github/workflows/test.yml` as a reusable workflow
   (`on: workflow_call` plus `on: [push, pull_request]` for direct PR feedback), with a
   `services: mariadb: image: mariadb:11.4` container so `TEST_DB_DSN` is always set in CI and
   the DB-backed tests actually run. GitHub Actions does not support `needs:` across files, so
   `deploy.yml` gains a `test: uses: ./.github/workflows/test.yml` job and the deploy job
   depends on it via `needs: test` — both in the same file, per the tech-spec's CI subsection.

## What to do

1. **Route `CONTACT_EMAIL` through all five hops.**
   - Add `CONTACT_EMAIL: ${{ secrets.CONTACT_EMAIL }}` to the `env:` block of the Deploy step
     in `.github/workflows/deploy.yml` (alongside the existing vars at lines 93-120).
   - Append `CONTACT_EMAIL` to the `envs:` comma-separated allowlist on the same step
     (`deploy.yml:126`).
   - Add `CONTACT_EMAIL=${CONTACT_EMAIL}` to the `.env` heredoc written on the server
     (`deploy.yml:234-260`).
   - Add `CONTACT_EMAIL: ${CONTACT_EMAIL}` to the `app.environment:` mapping in
     `docker-compose.prod.yml` (alongside the existing vars at lines 5-26).
   - Add `CONTACT_EMAIL: ${CONTACT_EMAIL:-}` to `app.environment:` in `docker-compose.yml`
     (dev compose) so local runs can exercise the banner too — follow the existing
     `${VAR:-default}` convention already used there for `DEEPSEEK_*`.
   - Document in decisions.md / task report that a `CONTACT_EMAIL` GitHub repository secret
     must be created before the next tagged deploy — this task cannot create the secret itself.

2. **Add `/auth/refresh` proxying and drop the dead `/auth/yandex` entry, in both nginx
   configs.**
   - In the heredoc-generated prod config inside `.github/workflows/deploy.yml` (~lines
     130-233): add a `location = /auth/refresh` block proxying to `http://poshivon_app:8080`
     with the same four `proxy_set_header` lines used by the neighboring `/auth/status` /
     `/auth/me` / `/auth/logout` / `/auth/yandex/code` blocks; remove the
     `location = /auth/yandex` block (Task 4 deletes that backend route — proxying to it now
     serves a 404 from the backend instead of a 200 from the SPA, but the entry is dead and
     should not linger).
   - Make the mirror edit in `client/nginx.conf:13-67` (dev-parity config): add
     `location = /auth/refresh` proxying to `http://app:8080` (note the dev service name is
     `app`, not `poshivon_app`), remove `location = /auth/yandex`.
   - Do not touch `deploy/nginx.conf` — code-research confirms it is a third, unused config
     that has no effect on production; editing it would be wasted work.

3. **Create `.github/workflows/test.yml` as a reusable + directly-triggered workflow.**
   - Trigger on `workflow_call` (so `deploy.yml` can invoke it) and on `[push, pull_request]`
     (so PRs get direct feedback without waiting for a tag).
   - Add a `services: mariadb: image: mariadb:11.4` service container with root password,
     database name, user/password matching what the test suite expects, and a health check
     (mirror the healthcheck shape already used for `db` in `docker-compose.yml:49-53` /
     `docker-compose.prod.yml:65-69`, adapted to GHA `services:` health-option syntax).
   - Set up Go (matching `server/Dockerfile`'s `ARG GO_VERSION=1.25.5`), and run
     `go test ./... -v` from the `server` module directory, passing `TEST_DB_DSN` pointing at
     the service container (`127.0.0.1:3306`, matching the mariadb service's exposed port) as
     an env var to the test step. `-v` is required per tech-spec so the log distinguishes an
     executed test from a `t.Skip`.
   - This task does not need to know the exact `TEST_DB_DSN` format string used by
     `store_test.go` — read whatever Task 3/4 actually wrote (the store/contract test file)
     to confirm the DSN shape expected, if it already exists by the time this task executes;
     otherwise use the standard `go-sql-driver/mysql` DSN form
     (`user:password@tcp(host:port)/dbname?parseTime=true`) consistent with `config.go`'s
     `DB_*` vars.

4. **Wire the test job into the deploy workflow within the same file.**
   - In `.github/workflows/deploy.yml`, add a `jobs.test: uses: ./.github/workflows/test.yml`
     job.
   - Add `needs: test` to the existing `build-and-deploy` job, in the same file — do not
     attempt a cross-file `needs:`, GitHub Actions does not support it.
   - Confirm the existing `on: push: tags: ["*"]` trigger on `deploy.yml` is unaffected —
     tagged pushes should still trigger both jobs, with `build-and-deploy` now blocked until
     `test` succeeds.

5. **Verify the admin row count on a deployed/migrated database** (does not require a new
   migration step — Task 1 already hardcodes both admin logins, `RoGogDBD` and
   `irina2000aleshina`, into `004_access_control.up.sql` via
   `INSERT ... ON DUPLICATE KEY UPDATE role='admin'`). This task's job is only to confirm the
   row count is 2 after a deploy that includes Task 1's migration — no placeholder
   substitution needed.

## Verification Steps

### Smoke

- `docker exec poshivon_app env | grep CONTACT_EMAIL` → variable present with the expected
  value (run after a deploy that includes the new secret and all five hops)
- `curl -i -X POST https://<host>/auth/refresh` → a JSON response from the backend (even an
  error JSON body counts — the point is it is not the SPA's `index.html`), not `Content-Type:
  text/html`
- Push to a branch (or open a PR) → confirm in the Actions tab that the `test` job in
  `deploy.yml` runs via `uses: ./.github/workflows/test.yml`, and that making a test fail
  (temporarily, locally, to confirm the gate — do not commit a broken test) blocks
  `build-and-deploy` from starting
- `docker exec poshivon_db mariadb -u<user> -p<password> <dbname> -e "SELECT COUNT(*) FROM
  users WHERE role='admin';"` → returns `2`
- `docker build` / local `go test ./... -v` against a locally-run `mariadb:11.4` container
  with `TEST_DB_DSN` set → confirms the `test.yml` service-container step works before relying
  on the hosted runner to prove it

**Edge cases:**
- `envs:` on the `appleboy/ssh-action` step is a flat comma-separated string — a typo or
  missing trailing/leading comma silently drops the variable with no error in the Action log;
  double-check the final list renders correctly.
- The `mariadb` service container in `test.yml` needs its own root/user/password env vars —
  these are CI-internal test credentials, not the prod `DB_*` secrets; do not reuse or
  reference prod secrets here.
- `docker-compose.yml` (dev) sets no `APP_STORAGE`, so it defaults to `MemoryRepository`
  even though it connects to and migrates MariaDB (`config.go:58`, confirmed in tech-spec's
  Agent Verification Plan section). This is a pre-existing dev quirk — do not "fix" it as
  part of this task; it is out of scope.
- Admin logins (`RoGogDBD`, `irina2000aleshina`) are already hardcoded into the migration by
  Task 1 — this task only verifies the resulting row count, it does not substitute
  placeholders or edit the migration file.
- `deploy/nginx.conf` is a dead, unused third nginx config (confirmed in code-research.md
  section 11) — do not edit it; it has zero effect on production.

**Implementation hints:**
- Keep the new `location = /auth/refresh` blocks textually identical in shape to the
  `/auth/status` / `/auth/me` / `/auth/logout` blocks immediately preceding them in each file
  — same four `proxy_set_header` lines, same `proxy_pass` target already used in that file
  (`poshivon_app:8080` in the deploy.yml heredoc, `app:8080` in `client/nginx.conf`).
- For the GHA `services:` health check on the mariadb container, GitHub Actions requires
  Docker-style `options:` with `--health-cmd`, not a YAML `healthcheck:` block — the syntax
  differs from Compose's `healthcheck:` even though the intent (wait for MariaDB to accept
  connections before running tests) is the same as the existing Compose healthchecks in
  `docker-compose.yml:49-53`.
- `deploy.yml`'s single job (`build-and-deploy`) becomes two: `test` (the reusable-workflow
  call) and `build-and-deploy` (`needs: test`, everything currently in the file). Nothing
  else about `build-and-deploy`'s steps should change.
