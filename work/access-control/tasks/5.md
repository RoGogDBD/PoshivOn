# Task 5: Эндпоинты доступа и администрирования, сборка маршрутов

## Required Skills

Before executing the task, load:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Это wave-5 задача, замыкающая контур доступа поверх `AccessService` (Task 2) и его репозиториев
(Task 3), и поверх идентичности в сессии, middleware и уже расширенного `buildRepositories`/
собранного в `main.go` `accessService` (Task 4, `RequireAuth` / `RequireAccess` /
`RequireAdmin` / `RequireSameOrigin` в `server/internal/handler/middleware.go`). Задача создаёт
сам HTTP-слой контура доступа — `AccessHandler` с четырьмя маршрутами из раздела Data Models
tech-spec (`GET /api/v1/access/me`, `POST /api/v1/access/requests`, `GET /api/v1/admin/users`,
`POST /api/v1/admin/users/{login}/access`) — и собирает в `server/cmd/main.go` все middleware-цепочки
для всех префиксов маршрутизации, а не только для нового контура: `/api/v1/users/` тоже должна
получить `RequireSameOrigin → RequireAuth → RequireAccess` в этой задаче, иначе middleware из
Task 4 останутся написанными, но не подключённым кодом. Также добавляется `CONTACT_EMAIL` в
конфигурацию (значение, которое `AccessHandler` отдаёт в ответе `GET /api/v1/access/me` для
плашки на клиенте), и расширяется `normalizePath` в `server/internal/handler/metrics.go` под
Decision 18: сегмент `{login}` в `/api/v1/admin/users/{login}/access` должен схлопываться в
`:id` в метке Prometheus независимо от формы значения, потому что `WithMetrics` оборачивает
`mux` снаружи авторизации (`CORS → Metrics → mux` в `main.go`) и путь попадает в метку до того,
как `RequireAdmin` успевает отклонить запрос.

В проекте сегодня нет ни одного HTTP-теста уровня handler (единственный существующий тестовый
файл — `server/internal/service/costing_test.go`, юнит-тесты на стабах). Эта задача создаёт
`httptest`-обвязку с нуля: сборка маршрутов и middleware-цепочек выносится в отдельную функцию
(по образцу того, что уже делает `buildRepositories` в `main.go` для репозиториев), чтобы
`access_test.go` и `middleware_test.go` вызывали ровно ту же функцию, что и `main()` — иначе
тесты проверяли бы копию обвязки, а не реальную сборку маршрутов, и рассинхрон между тестируемым
и реальным кодом остался бы незамеченным.

Нужно для завершения контура US-13 (админ не может выдать/снять доступ себе иначе как через
чужое решение), US-14 (администратор всегда имеет доступ), US-15 (владелец данных берётся из
сессии, не из адреса — хотя сам перенос `/api/v1/users/**` на сессию делает Task 6, здесь эти
маршруты уже должны быть закрыты `RequireAccess`), US-16 (пользователь без доступа отклоняется
на API), US-17 (устаревший `POST /auth/yandex` удаляется — маршрут больше не регистрируется в
`main.go`, поэтому обращение к нему даёт 404 от `http.ServeMux`, а не 401/403).

## What to do

1. **`server/internal/handler/access.go` (новый).** Создать `AccessHandler` с зависимостью на
   `*service.AccessService` — сверить точную сигнатуру конструктора с тем, что реально объявил
   Task 2 в `server/internal/service/access.go`, а не додумывать её. Отправка письма
   администраторам (`SMTPNotifier`) — это Phase 2, задача Task 16, и в эту задачу не входит
   вовсе: `AccessHandler` из Phase 1 не должен знать о нотификаторе.
   Реализовать четыре хендлера согласно таблице «Контракт API» в tech-spec (Data Models):
   - `GET /api/v1/access/me` — читает личность из `context` (положена туда `RequireAuth` из
     Task 4), возвращает `{login,display_name,email,role,has_access,request_status,contact_email}`
     (200) либо 401, если личности в контексте нет.
   - `POST /api/v1/access/requests` — создаёт заявку для текущего пользователя; 201 при успехе,
     409, если заявка уже `pending` или доступ уже выдан (см. правило в tech-spec: если доступ
     уже есть — 409 без обращения к репозиторию).
   - `GET /api/v1/admin/users` — только для `role=admin` (гарантируется `RequireAdmin`, но
     хендлер не должен сам решать про роль — это забота middleware); возвращает
     `{items:[UserRecord]}`.
   - `POST /api/v1/admin/users/{login}/access` — тело `{"granted": bool}`, декодируется через
     `decodeJSON` из `http.go` (уже отклоняет неизвестные поля через `DisallowUnknownFields`,
     что даёт требуемые 400 «неизвестное поле» бесплатно); переключает флаг и переводит заявку
     в `approved`/`rejected`; 204 при успехе, 404 для неизвестного `{login}`.
   Регистрация маршрутов — методом `Register(mux *http.ServeMux)` по образцу `APIHandler.Register`
   в `http.go`. Все ошибки домена (`ErrNotFound`, `ErrConflict`, и т.д. из `service/access.go`)
   проходят через `writeAPIDomainError` — не через `writeError` из `auth.go` (это отдельная,
   несовместимая конвенция ответа, используемая только в `auth.go`).

  Task 4**, эта задача их не трогает повторно; собирает только `AccessHandler` из уже готового
  `accessService`, навешивает middleware-цепочки на все префиксы из таблицы Architecture
  (регистрация `/auth/yandex` уже убрана Task 4), выносит сборку маршрутов в переиспользуемую
  функцию.

**Dependencies:**
- Task 3 (репозитории `UserRepository`/`AccessRequestRepository` в `MemoryRepository`/
  `PostgresRepository`) — эта задача не реализует репозитории, только подключает их через
  расширенный `buildRepositories`.
- Task 4 (`middleware.go`, идентичность в сессии, `HandleYandexLogin` удалена, ветки 403/409 в
  `writeAPIDomainError`, текст ошибок по Decision 17) — эта задача полагается на готовые
  `RequireAuth`/`RequireAccess`/`RequireAdmin`/`RequireSameOrigin` и на то, что `http.go` уже
  умеет 403/409; если что-то из этого не готово при выполнении задачи — прочитать фактическое
  состояние `middleware.go`/`http.go`, а не переписывать их здесь.
- Если сигнатура `AccessService`/`UserRepository`/`AccessRequestRepository`, фактически
  реализованная в Task 2/3, отличается от tech-spec — ориентироваться на фактический код, а не
  на tech-spec буквально, и зафиксировать отклонение в decisions.md по итогу.

**Edge cases:**
- `POST /api/v1/admin/users/{login}/access` на несуществующий `{login}` → 404, независимо от
  того, что `DecideRequest`/`SetAccess` в сервисе может по-разному трактовать «нет пользователя»
  vs «нет заявки» — наружу для незнакомого пользователя должен уйти именно 404, а не 500.
- Origin-проверка должна отклонять запрос ДО обращения к `AccessService`/репозиторию — все
  негативные case'ы в тестах должны также проверять, что состояние (флаг, заявка) не изменилось,
  а не только код ответа.
- Порядок цепочки — `RequireSameOrigin → RequireAuth → RequireAdmin`, как в таблице Architecture,
  и это даёт ровно два разных кода для двух разных негативных случаев, оба ожидаемые:
  `POST /api/v1/admin/users/x/access` **с корректным `Origin`, но без кук** → 401 (проверка
  источника пройдена, дальше отклоняет `RequireAuth`); тот же запрос **вовсе без заголовка
  `Origin`** → 403 (отклоняет `RequireSameOrigin`, до того как дело доходит до кук). Это не
  конфликт, а два разных теста на два разных входа — Verify-smoke в tech-spec специально
  задаёт `Origin` в первом случае и опускает во втором, чтобы различить их.
- Неизвестное поле в JSON-теле `POST .../access` → 400 благодаря `decodeJSON`
  (`DisallowUnknownFields`) — отдельной валидации не требуется, но нужно смотреть кодом, что
  `granted` действительно единственное ожидаемое поле.
- 500 с исходным SQL-текстом внутри ошибки репозитория не должен всплыть в теле ответа ни на
  одном из веток (400/404/409/429/500/503/504) — Decision 17 меняет общую функцию
  `writeAPIDomainError`, а не только новые ветки; проверить, что старые ветки (429/503/504 —
  сегодня определяемые через `strings.Contains` по тексту ошибки DeepSeek) не потеряли
  функциональность.

**Implementation hints:**
- Порядок `CORS → Metrics → mux` в `main.go` не меняется (Decision 18 полагается именно на этот
  порядок) — middleware нового контура (`RequireSameOrigin`/`RequireAuth`/`RequireAccess`/
  `RequireAdmin`) оборачивают отдельные хендлеры/группы маршрутов ВНУТРИ `mux`, не заменяют
  внешний порядок.
- `buildRepositories` — образец того, как в этом проекте уже расширяется кортеж возвращаемых
  репозиториев под разные бэкенды (`memory` vs `postgres/mysql/mariadb`) с общим `cleanup`.
- Стаб резолвера сессии для тестов — интерфейс, а не конкретный тип, потому что
  `auth.Store` требует `*sql.DB` и в `httptest`-окружении недоступен; сверить, не ввела ли
  Task 4 уже такой интерфейс в `middleware.go`.
