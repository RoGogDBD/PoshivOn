# Task 2: Доменный сервис доступа

## Required Skills

Before executing the task, load:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Создать `AccessService` — единственное место, где живут правила доступа: интерфейсы
`UserRepository` и `AccessRequestRepository`, тип `AccessRequest` (и сопутствующие
`AccessState`, `UserRecord`, `Role`), доменные ошибки `ErrForbidden` и `ErrConflict`, и сами
правила из Decision 3 (`has_access` — источник истины о доступе, не факт одобрения заявки),
Decision 5 (upsert-семантика `CreateRequest`: репозиторий сообщает число задетых строк,
сервис превращает ноль в `ErrConflict`; `decided_by`/`decided_at` переживают повторную подачу
на уровне репозитория — этот инвариант данная задача не реализует, но её тесты на стабах его
не нарушают), Decision 10 (администратор имеет доступ всегда, `has_access` у него
игнорируется) и Decision 11 (создание строки `users` при входе не должно сбрасывать
`role`/`has_access` — эта задача формулирует правило на уровне сервиса и стабов; сам
неразрушающий UPSERT в БД реализует Task 3 в `PostgresRepository`/`MemoryRepository`).

Эта задача не обращается к реальной БД: `UserRepository` и `AccessRequestRepository` —
только интерфейсы, реализуют их `PostgresRepository` и `MemoryRepository` в Task 3, который
зависит от этой задачи. Здесь правила проверяются на ручных стабах интерфейсов, по образцу
`CostingService`/`costing_test.go`.

Форма повторяет house style существующих интерфейсов сервисного слоя
(`server/internal/service/costing.go:168-183`): узкие интерфейсы объявлены в `service`,
`ctx` — первый аргумент, через границу проходят только доменные типы.

## What to do

- В `server/internal/service/access.go` объявить доменные типы `Role`, `AccessState`,
  `UserRecord`, `AccessRequest` — точно по сигнатурам из раздела "Data Models" tech-spec.md
  (`Доменные типы (server/internal/service/access.go)`).
- Там же объявить интерфейсы `UserRepository` (`EnsureUser`, `GetUser`, `ListUsers`,
  `SetAccess`) и `AccessRequestRepository` (`CreateRequest`, `GetRequest`, `DecideRequest`) —
  сигнатуры и семантика ошибок из того же раздела.
- В `server/internal/service/costing.go` рядом с существующими `ErrInvalidArgument` и
  `ErrNotFound` (строки 15-18) добавить `ErrForbidden` и `ErrConflict` в тот же блок `var`.
  Отдельного файла ошибок не заводить — оба существующих домена ошибок уже живут в
  `costing.go`, это одна точка для всего пакета `service`.
- Создать `AccessService` со скрытыми полями-зависимостями `UserRepository` и
  `AccessRequestRepository` (аналог `CostingService` — приватные поля, конструктор
  `NewAccessService`), и методами, реализующими правила:
  - `EnsureUser(ctx, login, email, displayName) error` — тонкая обёртка над
    `UserRepository.EnsureUser`; сама неразрушающая семантика обновления реализуется в Task 3,
    здесь сервис просто делегирует вызов репозиторию.
  - `GetAccessState(ctx, login) (AccessState, error)` (или аналогичный метод построения
    состояния доступа для `GET /api/v1/access/me`) — читает `UserRecord`, вычисляет итоговый
    флаг доступа как `HasAccess || Role == "admin"` (Decision 10) и заполняет `RequestStatus`.
  - `CreateRequest(ctx, login) error` — если у пользователя уже есть доступ
    (`HasAccess || Role == "admin"`), возвращает `ErrConflict` немедленно, не обращаясь к
    `AccessRequestRepository`; иначе вызывает `AccessRequestRepository.CreateRequest` и
    транслирует "ноль задетых строк" (через типизированную ошибку/сигнал от репозитория —
    определить контракт возврата, например репозиторий сам возвращает `ErrConflict`, когда
    `RowsAffected() == 0`) в `ErrConflict` вызывающей стороне.
  - `SetAccess(ctx, login string, granted bool, decidedBy string) error` — проверяет
    существование пользователя (`ErrNotFound`, если логина нет — через `UserRepository.GetUser`
    или прямой вызов `SetAccess` с транслируемой ошибкой репозитория), выставляет флаг через
    `UserRepository.SetAccess`, затем — только если у пользователя есть строка заявки —
    переводит её в `approved`/`rejected` через `AccessRequestRepository.DecideRequest` с
    `decidedBy`. Если строки заявки нет — `DecideRequest` не вызывается вовсе (не ошибка).
- Список литеральных статусов заявки (`"pending"`, `"approved"`, `"rejected"`) держать как
  простые строковые константы в `access.go`, по аналогии с тем, как `costing.go` не заводит
  enum-тип под `CalculatorMode`.
- Написать `server/internal/service/access_test.go` с ручными стабами `UserRepository` и
  `AccessRequestRepository` (in-memory maps, как `settingsRepoStub`/`chatRepoStub` в
  `costing_test.go`), покрывающими правила — см. TDD Anchor.
- Compile-time assertions (`var _ UserRepository = (*stubType)(nil)`) в тесте не обязательны —
  стабы используются напрямую как реализации интерфейсов в `AccessService`; проверяется
  сборка через `go build`/`go vet` при передаче стаба в конструктор.

## TDD Anchor

Tests to write BEFORE implementation. Write → run → confirm they fail → write code → confirm they pass.
Стабы репозиториев — ручные in-memory реализации `UserRepository`/`AccessRequestRepository`,
по образцу `settingsRepoStub`/`chatRepoStub` в `costing_test.go`; все тесты `t.Parallel()`.

- `server/internal/service/access_test.go::TestAccessService_NoAccessNoRequest_ReturnsEmptyState` —
  пользователь без доступа и без заявки: `HasAccess=false`, `RequestStatus=""`
- `server/internal/service/access_test.go::TestAccessService_AdminWithoutAccessFlag_HasAccess` —
  пользователь с `Role="admin"` и `HasAccess=false` считается имеющим доступ (Decision 10 / US-14)
- `server/internal/service/access_test.go::TestAccessService_CreateRequest_ByUserWithoutAccess_CreatesPending` —
  создание заявки пользователем без доступа: заявка создаётся со статусом `pending`
- `server/internal/service/access_test.go::TestAccessService_CreateRequest_RepoZeroRowsAffected_ReturnsErrConflict` —
  `CreateRequest` возвращает `ErrConflict`, когда репозиторий сообщает о нулевом
  `RowsAffected` (уже `pending`)
- `server/internal/service/access_test.go::TestAccessService_CreateRequest_UserAlreadyHasAccess_ReturnsErrConflictWithoutRepoCall` —
  заявка от пользователя, у которого уже есть доступ: `ErrConflict`, обращения к
  `AccessRequestRepository.CreateRequest` нет (стаб фиксирует факт вызова/невызова)
  — включая случай доступа через роль `admin`, не только через флаг
- `server/internal/service/access_test.go::TestAccessService_CreateRequest_AfterRejected_Allowed` —
  новая заявка после `rejected` разрешена (репозиторий возвращает успех, сервис не блокирует)
- `server/internal/service/access_test.go::TestAccessService_SetAccess_Grant_SetsFlagAndApprovesRequestWithDecidedBy` —
  `SetAccess(granted=true)` выставляет флаг и переводит существующую заявку в `approved`
  с `decided_by`
- `server/internal/service/access_test.go::TestAccessService_SetAccess_Revoke_UnsetsFlagAndRejectsRequest` —
  `SetAccess(granted=false)` снимает флаг и переводит заявку в `rejected`
- `server/internal/service/access_test.go::TestAccessService_SetAccess_UnknownLogin_ReturnsErrNotFound` —
  `SetAccess` для несуществующего логина возвращает `ErrNotFound`
- `server/internal/service/access_test.go::TestAccessService_SetAccess_NoExistingRequest_DoesNotCallDecideRequest` —
  `SetAccess` для пользователя без строки заявки не вызывает
  `AccessRequestRepository.DecideRequest` вовсе (стаб фиксирует факт вызова) и не считается
  ошибкой

## Acceptance Criteria

- [ ] Пользователь с `role='admin'` и `has_access=false` проходит проверку доступа
      (`AccessService` считает его имеющим доступ) — Decision 10, US-14
- [ ] `CreateRequest` для пользователя, у которого уже есть доступ (включая доступ через роль
      `admin`), возвращает `ErrConflict` без обращения к `AccessRequestRepository`
- [ ] `CreateRequest` транслирует нулевой `RowsAffected` от репозитория в `ErrConflict`
      (Decision 5)
- [ ] `SetAccess(granted=true)` выставляет флаг доступа и переводит существующую заявку в
      `approved` с `decided_by`; `SetAccess(granted=false)` — в `rejected`
- [ ] `SetAccess` не вызывает `DecideRequest`, если у пользователя нет строки заявки
      (не ошибка)
- [ ] `SetAccess` для несуществующего логина возвращает `ErrNotFound`
- [ ] `ErrForbidden` и `ErrConflict` объявлены в `server/internal/service/costing.go` рядом с
      `ErrInvalidArgument`/`ErrNotFound`
- [ ] Все правила покрыты юнит-тестами на стабах интерфейсов, тесты проходят (`go test ./internal/service/...`)

  → "Доменные типы" в tech-spec.md (строки ~474-527).
- `server/internal/service/access_test.go` (новый) — ручные стабы `UserRepository` и
  `AccessRequestRepository`, тесты по списку TDD Anchor.
- `server/internal/service/costing.go` — правка только блока `var` со строками 15-18: добавить
  `ErrForbidden = errors.New("forbidden")` и `ErrConflict = errors.New("conflict")` рядом с
  существующими `ErrInvalidArgument`/`ErrNotFound`. Остальной файл (`CostingService`,
  `BatchDiscount`, `PricingRules` и т.д.) не трогать.

**Dependencies:** зависит от Task 1 (миграция схемы) только логически — эта задача кода
миграции не касается и не обращается к БД; формальная зависимость `depends_on: [1]` фиксирует
порядок волн, а не реальную связь по коду.

**Edge cases:**
- Пользователь с `role="admin"` и `has_access=false` — доступ есть (Decision 10); то же
  верно и внутри `CreateRequest` (админ не может подать заявку — уже есть доступ, `ErrConflict`)
- `SetAccess` для пользователя без заявки не должен звать `DecideRequest` — стаб в тесте
  должен уметь зафиксировать факт вызова/невызова (например, счётчик или флаг в стабе)
- `CreateRequest` для пользователя, уже имеющего доступ, не должен обращаться к
  `AccessRequestRepository.CreateRequest` вовсе — это тоже проверяется через стаб (флаг вызова)
- Значения `RequestStatus` — только `""`, `"pending"`, `"approved"`, `"rejected"` (см. Data
  Models); других значений сервис не производит и не принимает

**Implementation hints:**
- `AccessService` — тонкий слой над двумя интерфейсами, без побочных эффектов вне вызовов
  репозиториев; вся ветвящаяся логика (кто имеет доступ, когда звать `DecideRequest`, когда
  возвращать `ErrConflict` до обращения к репозиторию) — здесь, а не в handler'ах или
  репозиториях, ради тестируемости на стабах без БД.
- Как именно репозиторий сигнализирует "ноль задетых строк" сервису — решить на этом слое:
  либо `AccessRequestRepository.CreateRequest` сам возвращает `ErrConflict` (тогда сервис
  просто пробрасывает ошибку через `errors.Is`), либо возвращает отдельную типизированную
  ошибку/значение, которое сервис транслирует в `ErrConflict`. В любом случае Task 3
  реализует репозитории под выбранный здесь контракт — сигнатуры интерфейсов из Data Models
  фиксированы (`CreateRequest(ctx, login) error`), поэтому контракт должен выражаться через
  ошибку, возвращаемую `CreateRequest`, а не через дополнительный параметр.
