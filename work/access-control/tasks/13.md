## Description

This is the acceptance-testing gate for Phase 1 (MVP) of "Доступ к панели по заявке с
одобрением администратором" — the last task before Deploy (Task 14). It depends on the three
audit tasks (10: Code Audit, 11: Security Audit, 12: Test Audit) that read the full set of
files changed across Tasks 1-9 and write their findings; this task does not re-read source
code. Its job is to run the existing automated test suite for real (against a live MariaDB,
not the in-memory fallback that silently skips the contractual tests) and to walk every
Phase-1 acceptance criterion from user-spec.md (US-1..US-17) and tech-spec.md's Acceptance
Criteria section, confirming each one is actually satisfied — not just that code exists that
claims to satisfy it.

The feature moves the access gate from "logged in via Yandex" to "granted access by an
admin," and does so by locking down `/api/v1/users/*`, `/api/v1/admin/*` and
`/api/v1/access/*` behind session-derived identity (Decisions 1, 6) and an `Origin` check
(Decision 8). Tech-spec explicitly separates a "Критерии Phase 2" sub-list at the end of its
Acceptance Criteria section (SMTP notification, styled UI) — Task 16-20 territory. This task
verifies only the Phase-1-scoped criteria; Phase 2 gets its own Pre-deploy QA (Task 18) after
Phase 1 ships.

A specific hazard called out in tech-spec's Testing Strategy → CI section: the contract test
suites in `server/internal/repository/access_repo_test.go` and
`server/internal/auth/store_test.go` (created in Tasks 3 and 4) run against `PostgresRepository`
/ real `oauth_sessions` rows only when `TEST_DB_DSN` is set — otherwise they `t.Skip()`, and
`go test` reports `ok` indistinguishably from a real pass. Tech-spec is explicit that this
is exactly the failure mode CI guards against by running a `mariadb:11.4` service container
and always setting `TEST_DB_DSN` (Task 9's `.github/workflows/test.yml`). This QA task must
reproduce that same condition locally/here — run with `TEST_DB_DSN` pointed at a live MariaDB
— or it is not actually verifying the load-bearing regression tests (the admin-demotion
invariant on `EnsureUser`, and `SetAccess` in both directions).

## What to do

1. Stand up a live MariaDB (e.g. `docker compose up -d db`, matching the `mariadb:11.4`
   version tech-spec pins) and export `TEST_DB_DSN` pointing at it, so the contract test
   suites in Tasks 3 and 4 actually execute instead of `t.Skip`-ing.
2. Run `go test ./... -v` from `server/` with `TEST_DB_DSN` set, and confirm the full suite
   passes — unit tests (`access_test.go`, `costing_test.go` — no regressions), the contract
   suites (`access_repo_test.go` against both `MemoryRepository` and `PostgresRepository`,
   `store_test.go`), and the handler/integration suites (`access_test.go`, `middleware_test.go`,
   `http_test.go`, `auth_test.go` under `server/internal/handler/`).
3. Inspect the verbose (`-v`) output line by line for every test tech-spec marks as
   load-bearing (see Details) and confirm each shows `--- PASS`, not `--- SKIP`. A skip on
   any of these means that criterion is not verified — treat it as a QA failure, not a pass,
   and do not report the run as green.
4. Walk the Phase-1 Acceptance Criteria list below one by one, and for each either point to
   the automated test that proves it, or run the equivalent manual check (curl / bash) when
   no automated test covers it directly (e.g. `SELECT COUNT(*) FROM users WHERE role='admin'`
   requires an environment with the migration applied).
5. Walk user-spec.md's US-1..US-17 the same way, cross-referencing against tech-spec's
   Acceptance Criteria and the "Agent verifies" table in user-spec.md's How to Verify section
   (steps 1-15) — these are largely the same ground covered from a different angle and both
   should be satisfied by the same evidence.
6. Explicitly confirm out of scope: US-5 (email notification) and the "Критерии Phase 2"
   sub-list at the end of tech-spec's Acceptance Criteria (email delivery, SMTP env vars,
   styled UI) are Phase 2 — Task 16-20 territory. Do not fail this task over them; note them
   as deferred/out-of-scope in the report, not as failing criteria.
7. Produce the JSON report (per pre-deploy-qa skill's output contract) — pass/fail per
   criterion, test-run summary, and any load-bearing skip treated as a failure.

## Details

**No source files are modified or read by this task.** Its job is running the existing test
suite (built by Tasks 1-9) and checking acceptance criteria — not reading or reviewing source.
That reading already happened in the Audit Wave (Tasks 10-12), which this task depends on.

**Fail loudly, not silently, on `TEST_DB_DSN` absence.** If `TEST_DB_DSN` is not set when
`go test ./... -v` runs, the contract suites in `server/internal/repository/access_repo_test.go`
and `server/internal/auth/store_test.go` call `t.Skip()` and the overall run still reports
`ok` — indistinguishable in a casual read from a real pass (tech-spec, Testing Strategy → CI,
makes this exact point about CI). This task must not report success on a run where those
suites skipped. Treat any `t.Skip` on a load-bearing test as "not verified" and fail the QA
gate, prompting for a live MariaDB DSN before re-running.

**Load-bearing tests that must show PASS, not SKIP** (per tech-spec's Testing Strategy
section — these are the ones explicitly called out as guarding real regressions, not just
incidental coverage):
- `server/internal/repository/access_repo_test.go`: `EnsureUser` для пользователя с
  `role='admin'` и `has_access=true` не сбрасывает ни то, ни другое — the admin-demotion
  regression guard for Decision 11.
- `server/internal/repository/access_repo_test.go`: `SetAccess` меняет флаг и виден
  последующему `GetUser`, в обе стороны — отдельно `granted=true` и отдельно
  `granted=false` — catches a zero-value reset bug that `MemoryRepository` cannot
  structurally reproduce, hence only meaningful against `PostgresRepository`.
- `server/internal/repository/access_repo_test.go`: existing write paths not broken —
  `UpsertSettings` and `CreateChat` for a new user succeed after the CHECK-constrained
  columns are added (Decision 13 regression guard).
- `server/internal/auth/store_test.go`: `CreateSession` сохраняет `yandex_login`,
  `yandex_email`, `yandex_display_name`.
- `server/internal/auth/store_test.go`: `UpdateSessionTokens` сохраняет личность при
  ротации токенов — without this, identity silently drops roughly at token-lifetime,
  a scenario a fresh-login test cannot reproduce.
- `server/internal/auth/store_test.go`: session with `NULL` `yandex_login` (pre-migration
  row emulation) reads cleanly via `FindByRefreshHash` — the basis for `RequireAuth`'s
  `session_identity_missing` fail-closed behavior (Decision 2); this path is only
  reachable against a real DB, not the handler-test session-resolver stub.

**Dependencies:** Task 10 (Code Audit), Task 11 (Security Audit), Task 12 (Test Audit) — all
three must have completed and their reports available; this task is the next gate after them,
before Task 14 (Deploy).

- Do not conflate "tests pass" with "all Phase-1 criteria met" — some criteria (e.g. env var
  propagation to the `poshivon_app` container, CI blocking deploy on failure) are

- `client/package.json` has no test runner (tech-spec, Client tests section) — do not expect
  or look for client unit tests; client behavior was covered by `Verify-user` in Tasks 7-8,
  not by an automated suite here.
