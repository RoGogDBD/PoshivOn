# Task 7: Клиентский гейт доступа и правки авторизации

## Required Skills

Before executing the task, load:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Задача закрывает клиентскую половину контура доступа: без неё серверный гейт из Task 6
(`RequireAuth` + `RequireAccess` на `/api/v1/`, Decision 6) и контур `access.go` из более
ранних волн видны пользователю только как голые 401/403 в консоли — рабочий интерфейс
панели продолжит рендериться и дёргать `/settings`, `/chats`, `/calculations` до первого
падения запроса. Нужно для US-1..US-4 (плашка вместо интерфейса, кнопка запроса, статус
«на рассмотрении»), US-11 (доступ выдан → рабочий интерфейс) и US-17 (закрытие обхода входа).

Пять правок, которые вместе дают результат:

1. **Слой вызовов контура доступа** — новый `client/src/utils/accessApi.js` с
   `GET /api/v1/access/me` (даёт `has_access`, `role`, `request_status`, `contact_email`) и
   `POST /api/v1/access/requests` (создаёт заявку, 409 при повторной подаче — Decision 5).
2. **Третий вызов в bootstrap-эффекте панели** (`Panel.jsx:192-224`) — сегодня эффект делает
   ровно два последовательных запроса (`checkAuthStatus`, `fetchAuthProfile`) и безусловно
   переводит `status` в `"ready"` (:215-217). Это единственная точка, через которую проходит
   каждый рендер `/panel` (Decision 15) — сюда добавляется третий вызов `GET /api/v1/access/me`.
3. **Значение `no-access` в машине состояний `status`** (`Panel.jsx:171`) — сегодня в ней
   только `"checking"`/`"ready"`, нет состояния отказа (обе неудачи bootstrap просто редиректят
   на `/`, :199, :210). Рендер-гейт `:547-555` также ветвится только по `status !== "ready"`.
4. **Охрана эффектов загрузки данных** (`Panel.jsx:230-278` — `loadSettings`/`loadChats`,
   `:280-308` — история) — они триггерятся по `userID`, который выставляется вместе с
   `profile` на `:207`, то есть до и независимо от результата проверки доступа. Без охраны
   пользователь без доступа всё равно отправит `GET /settings` и `GET /chats` до того, как
   плашка появится на экране — это прямое нарушение AC «пользователь без доступа не отправляет
   запросов к /settings, /chats, /calculations».
5. **Функциональная плашка** `client/src/components/AccessRequestBanner.jsx` — показывает
   контактный email и кнопку «Запросить доступ»; `AuthModal.jsx` для этого не переиспользуется:
   он рендерится только с лендинга (`App.jsx:50`) и не смонтирован на `/panel` (`App.jsx:34-35`
   возвращает `<Panel />` раньше, чем строится дерево лендинга) — плашка должна жить внутри
   дерева `Panel.jsx`.

Отдельно — правки авторизации по Decision 7, 9, 12: `buildYandexAuthUrl` (`yandexAuth.js:125-142`)
сегодня не передаёт ни `scope`, ни `state`, и implicit-ветка в `AuthCallback.jsx:31-45` (плюс
`persistYandexToken`, `yandexAuth.js:61-79`) всё ещё существует, хотя штатный вход её не создаёт —
`buildYandexAuthUrl` формирует только `response_type=code`, поэтому `#access_token=...` в хэше
может появиться только при ручном формировании URL атакующим. Серверный `POST /auth/yandex`
удаляется отдельной (более ранней) задачей — здесь убирается клиентский код, который на него
опирался.

Наконец, адреса существующих вызовов в `panelApi.js` (`/api/v1/users/{userID}/...`) переводятся
на контракт Task 6 — без сегмента `userID`, владелец берётся из сессии на сервере.

**Edge cases:**

  должен запускать retry-логику `authFetch`/`shouldRefreshAuth` (`yandexAuth.js:14-16`) — она и
  так реагирует только на `status === 401` с одним из трёх кодов (`access_cookie_missing`,
  `access_expired`, `access_mismatch`), так что 403 уже проходит мимо нее без правок; проверить
  при ревью, что это осталось так — 403 НЕ добавляется в список кодов, запускающих refresh.
  Главная защита от таких 403 — не обработка ответа, а то, что охрана эффектов (:230-278,
  :280-308) вообще не даёт этим запросам уйти для пользователя без доступа.
- Заявка уже `pending` при повторном клике — 409 от `createAccessRequest`, плашка показывает
  тот же текст «на рассмотрении», не текст ошибки.
- Заявка от пользователя, у которого доступ уже выдан (например, выдан администратором между
  загрузкой панели и кликом) — тоже 409 (Decision 5, AC тех-спека); тот же путь обработки, что и
  «уже pending», плашка при этом всё равно не должна быть видна следующей перезагрузкой, так как
  `has_access` станет истинным.
- `default_email` отсутствует в ответе Яндекса (Decision 12) — `access/me` в этом случае отдаёт
  пустой `email`; плашка и приветствие не должны падать на пустом email, это ожидаемое значение,
  не ошибка загрузки.
- URL с `#access_token=...` в хэше, но также с `code` в query (маловероятно, но возможно при
  ручном формировании) — после удаления implicit-ветки такой URL пойдёт по обычной `code`-ветке;
  это ожидаемо и не требует отдельной обработки — приоритет `code` уже заложен структурой кода
  (:47 проверяется независимо от хэша).
- `state` отсутствует в `sessionStorage` вовсе (например, пользователь открыл `/auth?code=...`
  напрямую, минуя `buildYandexAuthUrl`) — считается несовпадением, вход прерывается тем же
  путём, что и явное расхождение значений.

**Implementation hints:**
- `state` — случайная строка на клиенте, например через `crypto.randomUUID()` (доступен в
  браузерах, которые поддерживает текущий Vite-таргет) или `crypto.getRandomValues`; не
  привязывать к `Math.random()` — это не про криптостойкость самого токена OAuth (им остаётся
  код авторизации), а про непредсказуемость для защиты от CSRF при связывании ответа с
  инициировавшим браузером (Decision 9).
- Порядок проверок в `AuthCallback` до правки уже такой: `error` → (было: `access_token`) →
  `code` → `finalize("error")`. После правки порядок: `error` → сверка `state` (только если есть
  `code`, иначе смысла в сверке нет — тогда путь идёт в `finalize("error")` как и сегодня) →
  `code` → `exchangeYandexCode`.
- Определение доступа на клиенте — зеркало серверного `has_access || role == 'admin'`
  (Decision 10); держать в одном месте (например, в `Panel.jsx` рядом с местом, где сохраняется
  результат `fetchAccessState`), не размазывать по компоненту и баннеру.
- Проверка `Origin` (Decision 8) на `POST /api/v1/access/requests` — целиком серверная,
  browser расставляет заголовок `Origin` на `fetch` с телом/методом не-GET автоматически;
  клиентских правок для этого не требуется.
