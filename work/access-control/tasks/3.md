## Description

Task 2 declared `UserRepository` and `AccessRequestRepository` in `server/internal/service/access.go`
as narrow interfaces (see tech-spec Data Models, `server/internal/service/access.go`), following
the existing house style where `service` owns interfaces and `repository` owns implementations
(mirrors `service.UserSettingsRepository`, `service.ChatRepository`, `service.ChatCalculationRepository`
already implemented by both `PostgresRepository` and `MemoryRepository`). This task implements
both interfaces in both stores.

The production repository is `PostgresRepository` (`server/internal/repository/postgres.go`), backed
by GORM over MariaDB. It already writes to the `users` table via `upsertUser` — a helper called from
three existing write paths (`UpsertSettings` at postgres.go:140, `CreateChat` at postgres.go:233,
`AppendCalculation` at postgres.go:363) that inserts a bare `userModel{ID: userID}` with `DoNothing: true`
on conflict. `userModel` (postgres.go:15-22) currently has only `ID` and `CreatedAt`. Decision 13 is a hard
constraint verified live against MariaDB 11.4: adding `Role`/`HasAccess`/`Email`/`DisplayName` fields to
`userModel` makes GORM include those columns (with Go zero values, e.g. `role=''`) in the `INSERT` on
these three existing call sites, which violates the new `chk_users_role CHECK (role IN ('user','admin'))`
constraint added by Task 1's migration (`ERROR 4025 (23000): CONSTRAINT chk_users_role failed`) — breaking
settings save, chat creation, and calculation append for any user who has never logged in through the new
`EnsureUser` path. So `userModel` stays untouched, and a **separate** GORM model, mapped to the same
`users` table via `TableName() string { return "users" }`, is introduced to read/write the access columns
(`role`, `has_access`, `email`, `display_name`).

`MemoryRepository` (`server/internal/repository/memory.go`) is the in-memory store used when
`APP_STORAGE=memory` (see `buildRepositories` in `server/cmd/main.go`) and in tests; it needs equivalent
in-memory implementations of the same two interfaces, guarded by the existing `sync.RWMutex` (`r.mu`).

This is the production storage layer that every authorization decision in this feature (`RequireAuth`,
`RequireAccess`, `RequireAdmin` in Task 4, and the `/api/v1/access/*` and `/api/v1/admin/users*` handlers
in Task 5) ultimately reads from and writes to. A bug here — a lost gorm tag, a swapped upsert branch, an
admin role silently reset on login — is a security bug, not just a functional one, which is why this task
also delivers a contract test suite that runs the exact same assertions against both stores, and against
the real MariaDB when `TEST_DB_DSN` is set.

Note: `buildRepositories` in `server/cmd/main.go` currently returns a fixed 3-tuple
(`service.UserSettingsRepository, service.ChatRepository, service.ChatCalculationRepository, func(), error`)
and is NOT touched by this task — widening it to also return the two new repositories is Task 5's job
(wiring `AccessHandler` and route assembly). This task only makes both `PostgresRepository` and
`MemoryRepository` satisfy `UserRepository`/`AccessRequestRepository`; nothing outside the `repository`
package changes.

## What to do

1. In `server/internal/repository/postgres.go`, add a new GORM model mapped to the `users` table
   for the access columns (`role`, `has_access`, `email`, `display_name`), keeping `userModel`
   (ID + CreatedAt only) completely unchanged — add a comment at `userModel`'s declaration stating
   the invariant that it must never gain access columns, and why (Decision 13, `ERROR 4025`).
2. Implement `UserRepository` on `*PostgresRepository`:
   - `EnsureUser(ctx, login, email, displayName)` — `INSERT ... ON DUPLICATE KEY UPDATE` (via GORM
     `clause.OnConflict` with an explicit `DoUpdates` column list) limited to `email` and
     `display_name` only; `role` and `has_access` must never appear in the update list (Decision 11).
   - `GetUser(ctx, login)` — returns `service.UserRecord` populated with `role`/`has_access` (plus
     email, display_name, created_at); maps "no row" to `service.ErrNotFound`.
   - `ListUsers(ctx)` — all rows from `users`, including users created only through `EnsureUser`
     (no settings/chats yet).
   - `SetAccess(ctx, login, granted)` — updates `has_access` for the given login; maps "no row
     affected" to `service.ErrNotFound`.
3. Implement `AccessRequestRepository` on `*PostgresRepository` against the `access_requests` table
   created by Task 1's migration:
   - `CreateRequest(ctx, login)` — run exactly the upsert SQL from Decision 5 (quoted below) via
     `tx.Exec`/raw SQL (GORM's `clause.OnConflict` cannot express the conditional `IF(...)` branches),
     inspect `sql.Result.RowsAffected()`: `0` → `service.ErrConflict` (already pending), `1` or `2` →
     success. Do not use `clientFoundRows` — `server/internal/db/db.go` does not set it, so the driver
     returns MySQL "affected rows" semantics (1=insert, 2=real update, 0=no-op), matching Decision 5.
   - `GetRequest(ctx, login)` — returns `service.AccessRequest`; maps "no row" to `service.ErrNotFound`.
   - `DecideRequest(ctx, login, status, decidedBy)` — updates `status`, `decided_at` (now), `decided_by`
     on the existing row; a login with no request row is NOT an error (per Decision 5's contract —
     `DecideRequest` for a user with no request row is a no-op, not a failure).
4. Implement the same two interfaces on `*MemoryRepository` using new maps guarded by the existing
   `r.mu`, replicating the same semantics (including the pending-conflict and rejected-then-reapply
   behavior of `CreateRequest`, and the admin-preserving behavior of `EnsureUser`) purely in Go —
   no SQL involved, but the observable behavior (errors returned, which fields are updated) must match
   the Postgres implementation exactly, since both are exercised by the same contract tests.
5. Add compile-time interface assertions for both new interfaces on both repos, next to the existing
   ones (`postgres.go:97-99`, `memory.go:28-30`):
   `var _ service.UserRepository = (*PostgresRepository)(nil)`,
   `var _ service.AccessRequestRepository = (*PostgresRepository)(nil)`, and the `MemoryRepository`
   equivalents.
6. Write `server/internal/repository/access_repo_test.go` as a contract suite: one set of
   `TestAccessRepoContract_*` functions, each taking `t *testing.T` and a
   `factory func() (service.UserRepository, service.AccessRequestRepository)`, invoked twice from
   top-level `Test...` functions — once always against `NewMemoryRepository()`, once against
   `NewPostgresRepository(...)` opened from `TEST_DB_DSN` (via `t.Skip` when the env var is unset).
   Include three existing-write-path regression tests (`UpsertSettings`, `CreateChat`, and
   `AppendCalculation` for a brand-new user — `AppendCalculation` also calls `upsertUser` at
   postgres.go:363, carrying the same Decision 13 risk as the other two) as part of the same
   file, run only against the DB-backed factory since they exercise the real CHECK constraint.

Exact upsert SQL for `CreateRequest` (Decision 5, verified live against `mariadb:11.4`):

```sql
INSERT INTO access_requests (user_id, status, created_at)
VALUES (?, 'pending', ?)
ON DUPLICATE KEY UPDATE
  status     = IF(status = 'pending', status, VALUES(status)),
  created_at = IF(status = 'pending', created_at, VALUES(created_at))
```

## TDD Anchor

Tests to write BEFORE implementation. Write → run → confirm they fail → write code → confirm they pass.
All contract functions live in `server/internal/repository/access_repo_test.go`, take
`(t *testing.T, factory func() (service.UserRepository, service.AccessRequestRepository))`,
and are invoked twice — once against `MemoryRepository` (always), once against `PostgresRepository`
(when `TEST_DB_DSN` is set, `t.Skip` otherwise):

- `TestAccessRepoContract_EnsureUserCreatesUser` — `EnsureUser` on an unknown login creates a row
  with `role='user'`, `has_access=false`
- `TestAccessRepoContract_EnsureUserPreservesAdminRoleAndAccess` — **the single most important test
  in this file**: `EnsureUser` called for a login whose row already has `role='admin'`,
  `has_access=true` changes neither field on repeat call; this is the admin-demotion regression test
  for Decision 11 — without it, the second admin login after deploy silently strips their role
- `TestAccessRepoContract_EnsureUserUpdatesProfileFields` — repeat `EnsureUser` call with a new
  `email`/`displayName` updates those two columns
- `TestAccessRepoContract_GetUserReturnsRoleAndAccess` — `GetUser` returns non-empty `Role` and the
  correct `HasAccess` bool; catches a lost gorm tag on the separate access-columns model
- `TestAccessRepoContract_GetUserUnknownLoginNotFound` — `GetUser` for an unknown login →
  `service.ErrNotFound`
- `TestAccessRepoContract_SetAccessGrant` — `SetAccess(login, true)` on a user with
  `has_access=false` is visible in a later `GetUser` as `true`
- `TestAccessRepoContract_SetAccessRevoke` — `SetAccess(login, false)` on a user with
  `has_access=true` is visible in a later `GetUser` as `false`; run as a separate test function from
  the grant direction — a Go zero-value bug in the write path would silently look correct on
  `MemoryRepository`'s map-backed store and only surface against the real DB
- `TestAccessRepoContract_SetAccessUnknownLoginNotFound` — `SetAccess` for an unknown login →
  `service.ErrNotFound`
- `TestAccessRepoContract_ListUsersIncludesLoginOnlyUsers` — `ListUsers` returns every row,
  including users created only via `EnsureUser` with no settings/chats
- `TestAccessRepoContract_CreateRequestConflictWhilePending` — `CreateRequest` called twice while
  the row is `pending`: the second call returns `service.ErrConflict`, verified through
  `RowsAffected() == 0` on the Postgres path, not just the returned error
- `TestAccessRepoContract_DecideRequestPreservesDecision` — `DecideRequest` sets and preserves
  `decided_by`/`decided_at` on the row
- `TestAccessRepoContract_DecideRequestNoRowIsNotError` — `DecideRequest` for a login with no
  request row at all does not return an error
- `TestAccessRepoContract_CreateRequestAfterRejectedSucceeds` — after a request was decided
  `rejected`, a new `CreateRequest` for the same login succeeds (`RowsAffected() != 0` on the
  Postgres path), the row's status moves back to `pending`, and the prior `decided_by`/`decided_at`
  survive the upsert
- `TestAccessRepoContract_ExistingWritePathsSurviveAccessColumns` — DB-backed only (needs the real
  CHECK constraint from Task 1's migration): `UpsertSettings`, `CreateChat`, and `AppendCalculation`
  all succeed for a brand-new user after the access columns and `chk_users_role` exist on `users`; this is the
  Decision 13 regression test — it is the one that would have caught
  `ERROR 4025 (23000): CONSTRAINT chk_users_role failed` had `userModel` been extended instead of
  using a separate model

**Dependencies:** Task 2 (`server/internal/service/access.go` must exist with the
`UserRepository`/`AccessRequestRepository` interfaces, `service.AccessRequest`, `service.UserRecord`,
`service.ErrForbidden`, `service.ErrConflict` before this task's code compiles); Task 1's migration
(`server/migrations/004_access_control.up.sql`) must be applied against the test DB for the
DB-backed contract cases and the `chk_users_role` regression test to run meaningfully.

**Edge cases:**
- `EnsureUser` must never include `role`/`has_access` in its `ON DUPLICATE KEY UPDATE` column list —
  the single biggest risk in this task (Decision 11 admin-demotion regression).
- `CreateRequest`'s `RowsAffected()` semantics depend on `go-sql-driver/mysql` NOT having
  `clientFoundRows=true` in the DSN — confirm `server/internal/db/db.go` still doesn't set it before
  relying on 1/2/0 semantics.
- `DecideRequest` for a login with no request row is defined as a no-op, not an error — do not wire
  it to return `ErrNotFound`; the tech-spec is explicit that `SetAccess` (Task 2, service layer) never
  calls into `AccessRequestRepository` when there is no existing request, so this repository-level
  behavior matters mainly for direct/administrative decisions.
- `SetAccess` mapping "no row updated" to `ErrNotFound` needs `RowsAffected()` on the Postgres side
  and an explicit map-key check on the Memory side — don't rely on GORM's `.Error` alone, a no-op
  `UPDATE ... WHERE id = ?` on an absent row returns `nil` error with 0 rows affected.
- `MemoryRepository`'s `SetAccess(login, false)` must actually flip a stored `true` back to `false` —
  a common bug is only ever setting `true` because the caller reuses a struct literal without zeroing
  the field; this is exactly the case the DB-backed direction of the same test would also catch, but
  cover it on Memory too since it always runs.

**Implementation hints:**
- Follow the existing pattern for the separate access-columns model: same shape as `userModel`
  (`TableName() string { return "users" }`), gorm column tags matching the migration's column names
  (`role`, `has_access`, `email`, `display_name`), primary key on `id`.
- `CreateRequest`'s raw SQL should run through `tx.Exec(...)` (or `r.db.WithContext(ctx).Exec(...)`)
  so the underlying `sql.Result` is reachable for `RowsAffected()` — GORM's `.Create()`/`.Save()`
  wrappers do not expose it the same way.
- For `MemoryRepository`, replicate the pending/rejected upsert semantics with plain Go conditionals
  under the existing mutex — no need to simulate `RowsAffected()` values, only the resulting error
  (`ErrConflict` vs success) and final row state need to match.
