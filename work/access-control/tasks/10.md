## Description

This is the Audit Wave gate for the "Доступ к панели по заявке с одобрением администратором"
(access-control) feature — it runs after Waves 1-8 (Tasks 1-9) have implemented the entire
Phase 1 MVP: the DB migration, the domain service, both repository implementations, session
identity + auth middleware, the access/admin HTTP endpoints, the migration of existing
`/api/v1/users/*` routes to session-derived ownership, the client-side access gate, the admin
"Пользователи" section, and the deploy/CI wiring.

Each of Tasks 1-9 was reviewed individually (by `code-reviewer`, `security-auditor`,
`test-reviewer`/`deploy-reviewer` as applicable) while looking at its own diff in isolation.
This task is different: it is a **holistic, cross-component** pass over the feature as a
whole, done only after every piece exists. Its job is to catch problems that are invisible
from inside a single task's diff — for example: a resource constructed twice because two
tasks each assumed they owned it, a middleware chain that's internally consistent per-file but
inconsistent once assembled in `main.go`, or an interface implemented with a different style
in `postgres.go` than in `memory.go`. Per the project's skills-and-reviewers catalog, an audit
task has no reviewers of its own — the audit itself *is* the review, performed by the agent
executing this task using the `code-reviewing` skill's methodology.

This task writes no code. Its sole deliverable is a written audit report with findings (or a
clean bill of health), plus a brief summary appended to `decisions.md`.

  tech-spec — the audit's value is catching drift between the plan and what actually landed.
- Review holistically for cross-component issues, in particular:
  - **Duplicate resource initialization.** Check the Shared resources table in tech-spec.md's
    Architecture section (`*sql.DB`, `*gorm.DB`, `SMTPNotifier`, `AccessService`) against
    `server/cmd/main.go` as it exists after Task 9 — each of `*sql.DB` and `*gorm.DB` must be
    constructed exactly once and threaded through, `AccessService` must be constructed exactly
    once and shared between `AccessHandler`, `AuthHandler` (only its `EnsureUser` method per
    the table), and the middleware chain — not re-constructed per-handler or per-route.
  - **Middleware chain consistency.** Cross-check the route-to-middleware table in tech-spec.md's
    "Маршруты и их обвязка" against the actual registration in `main.go`: `/api/v1/users/`
    must carry `RequireSameOrigin → RequireAuth → RequireAccess`, `/api/v1/admin/` must carry
    `RequireSameOrigin → RequireAuth → RequireAdmin`, `/api/v1/access/` only
    `RequireSameOrigin → RequireAuth` (deliberately no `RequireAccess` — see Decision 6's note
    on why), and `POST /auth/yandex/code`, `POST /auth/refresh`, `POST /auth/logout` only
    `RequireSameOrigin`.
  - **Architectural consistency with the house style** established in tech-spec.md's Data
    Models section: narrow interfaces (`UserRepository`, `AccessRequestRepository`) declared in
    `service`, implemented by structs in `repository`, `ctx` as the first argument, only domain
    types crossing the boundary (mirrors the existing `costing.go:168-183` style). Check that
    `postgres.go` and `memory.go` both honor this rather than one of them leaking storage-layer
    types or diverging in method signatures.
  - **The `userModel` invariant from Decision 13** — confirm `userModel` in `postgres.go` still
    contains only `ID` and `CreatedAt`, and that the access-columns model introduced by Task 3
    is genuinely separate, with the "does not contain access columns" invariant still marked by
    a comment as required.
  - **Error-text consistency (Decision 17)** — confirm `writeAPIDomainError` in `http.go` gives
    every branch (400/401/403/404/409/429/500/503/504) a fixed, category-bound message across
    all the tasks that touch it (Task 4 introduces the pattern, Task 5/6 add call sites), and
    that no branch anywhere in the touched files still returns `err.Error()` to the client.
  - Any other duplication, inconsistency, or drift between what Tasks 1-9 individually claim to
    have done (per their own descriptions in tech-spec.md) and what the assembled codebase
    actually shows when read end-to-end.
- Write the audit report to
  `work/access-control/logs/working/task-10/code-audit.md` — structured findings (severity,
  location, description, suggested fix) per file/dimension, or an explicit statement that no
  issues were found for a given dimension.
- Do **not** modify any code. If a finding looks trivial to fix, still only report it — fixing
  is out of scope for this task; a human or a follow-up task decides whether/how to act on
  findings.
- Append a brief summary to `decisions.md` per Post-completion below, linking to the full
  report.

## Details

**Files:** none are modified by this task — see Context Files above for the full read-only
file list (union of Tasks 1-9 "Files to modify" from tech-spec.md).

**Dependencies:** depends on Tasks 1-9 (Waves 1-8) all being complete — this task cannot start
until the entire Phase 1 MVP implementation exists to be audited. Runs before Task 11
(Security Audit) and Task 12 (Test Audit) conceptually, but per tech-spec.md's Audit Wave
grouping these three audits are independent of each other and can run in parallel — this task
covers code quality/architecture, not security (Task 11) or test quality (Task 12); avoid
duplicating their scope, though noting an overlap finding is fine if it's clearly relevant to
architectural consistency.

**Edge cases / things easy to miss in a per-task review but visible only holistically:**
- `server/cmd/main.go` is touched by three different tasks (4, 5, and implicitly whatever Task
  9's deploy wiring assumes about it) — this is exactly where duplicate construction of
  `*sql.DB`, `*gorm.DB`, or `AccessService` would most likely slip in, since each task's author
  saw only their own diff against `main.go`, not the merged result.
- `server/internal/handler/access.go` and `server/internal/handler/http.go` are each touched by
  two tasks (5+6 and 4+6 respectively) — check for logic that got half-migrated (e.g. one route
  still reading `userID` from the URL segment after Task 6 was supposed to remove that
  entirely, per Decision 6).
- `client/src/pages/Panel.jsx` is touched by both Task 7 (bootstrap gate) and Task 8 (admin
  section) — check the merged component for duplicated state or two independent effects doing
  overlapping work.
- Compile-time interface assertions (`server/internal/repository/memory.go:28-30` pattern) —
  confirm both `PostgresRepository` and `MemoryRepository` still have them for
  `UserRepository`/`AccessRequestRepository` after Task 3, and that Task 6's edits to
  `http.go`/`access.go` didn't require widening either interface without updating both
  implementations.

**Implementation hints:** work file-by-file within each of the three groups (server, client,
deploy), then do one final pass specifically hunting cross-file issues (grep for repeated
`db.Open`/`db.OpenGORM`/`NewAccessService`-style constructor calls across `main.go`; diff the
method sets of `UserRepository`/`AccessRequestRepository` against both implementing structs).
Use the `code-reviewing` skill's 11 dimensions as the checklist, but apply them at the feature
level, not per-file.
