## Description

Full-feature test quality audit of the access-control feature (Phase 1 — Tasks 1-9). This is
the third audit in the Audit Wave, after Code Audit (Task 10) and Security Audit (Task 11).
No code is written or fixed here — the deliverable is a written audit report.

The feature rewrote the entire authorization model: personal identity moved into the session,
access state moved onto `users`, every `/api/v1/` route gained an authorization gate, and the
raw-token login bypass was closed. Tech-spec's Testing Strategy (`tech-spec.md` → "Testing
Strategy", lines 594-742) prescribes a specific two-level test pyramid for this: authorization
*rules* covered by unit tests, and *application* of those rules to real routes covered by
integration tests through the actual `http.ServeMux` wiring from `main.go` (not a copy of it).
Several of the prescribed tests exist specifically to catch bugs that are otherwise invisible —
an admin-demotion regression, a Go zero-value bug that only manifests against Postgres, and an
Origin-check branch that silently changed direction during tech-spec revision (Decision 8). This
audit verifies those load-bearing tests actually exist in the code and actually assert what the
tech-spec says they must — not just that "some test file with a similar name" is present.

## What to do

Read every test file the feature produced, and read `tech-spec.md`'s Testing Strategy section as
the coverage baseline (it is the authoritative bullet list — go through it bullet by bullet):

- `server/internal/service/access_test.go` (Task 2)
- `server/internal/repository/access_repo_test.go` (Task 3)
- `server/internal/auth/store_test.go` (Task 4)

- `server/internal/handler/middleware_test.go` (Task 4/5)
- `server/internal/handler/http_test.go` (Task 6)

For each file, check against the corresponding Testing Strategy bullets:
- Does a test exist for every bullet, or is something from the tech-spec's list silently missing?
- Do assertions actually check the claimed behavior (state, response body, side effects), or do
  they just check "no error" / a status code without verifying the effect (e.g. a 403 test that
  never re-reads the flag to confirm it did not change)?
- Is the test pyramid balanced the way tech-spec intends — unit tests on stubs for pure service
  rules, integration tests through `httptest` + real `ServeMux` wiring for route-level
  authorization, contract tests run against both `MemoryRepository` and `PostgresRepository`
  (via `TEST_DB_DSN`) where the tech-spec calls for both?
- Any test that looks tautological, disabled (`t.Skip` without the intended `TEST_DB_DSN` guard),
  or asserting something trivially true regardless of the code under test?

Give specific, deliberate attention to the load-bearing cases the tech-spec calls out by name
(these are exactly the ones a shallow pass would rubber-stamp as "looks fine, moving on"):

1. **Admin-demotion regression** — `EnsureUser` for an existing row with `role='admin'`,
   `has_access=true` must NOT reset either field on a repeat login (Decision 11). Confirm
   `access_repo_test.go` has this exact case and asserts both fields survive, not just that the
   call doesn't error.
2. **`SetAccess(granted=false)` direction, DB-tested** — tech-spec explicitly requires this
   against `PostgresRepository`, not only `MemoryRepository`, because a Go zero-value bug (an
   unset `bool` field defaulting to `false`) can silently "work" on a map-backed store while
   failing to actually write `false` through an ORM/SQL layer. Confirm both directions
   (`granted=true` and `granted=false`) are asserted, and that the `false` direction runs under
   `TEST_DB_DSN` against the real repository, not just the in-memory stub.
3. **`CreateRequest` upsert semantics via `RowsAffected`** — confirm the tests check the actual
   `RowsAffected()` count (0 on a no-op conflict, 1 or more on a real insert/update) rather than
   only checking the returned error, for: first request (insert), duplicate while `pending`
   (`ErrConflict`, `RowsAffected() == 0`), and re-request after `rejected` (succeeds,
   `RowsAffected() != 0`, prior `decided_by`/`decided_at` preserved).
4. **Origin-check branch matrix (Decision 8)** — confirm `access_test.go` and/or
   `middleware_test.go` cover all five branches, each verified by re-checking that the access
   flag did not change on the rejected branches: no `Origin` header → 403; foreign `Origin` with
   non-empty `CORS_ALLOWED_ORIGINS` → 403; `Origin` equal to `r.Host` with **empty**
   `CORS_ALLOWED_ORIGINS` → passes (same-origin fallback); foreign `Origin` with empty
   `CORS_ALLOWED_ORIGINS` → still 403 (not a pass-through); `GET` request with missing/foreign
   `Origin` → not blocked (method is exempt). Also confirm `auth_test.go` covers the login-CSRF
   variant of this on `POST /auth/yandex/code`.
5. **No internal error text leaks, across ALL branches** — confirm the assertion that
   `writeAPIDomainError` never leaks the underlying error string is exercised across every status
   branch tech-spec lists (400/403/404/409/429/500/503/504), not only the branches newly added by
   this feature. If only the new branches (403/409) are tested and the pre-existing branches
   (400/404/429/500/503/504) are untested or untested-for-leakage, flag it as a gap even though
   the feature didn't touch those branches' logic — tech-spec asks for full coverage here.

Also check the two exclusions tech-spec declares deliberately (these are not gaps, confirm they
are intentional and correctly scoped, not accidentally missing coverage):
- **Client tests: none** — no test runner exists in `client/package.json`; confirm no client test
  files were silently expected/missing, and that `test-reviewer` was correctly excluded from
  client-touching tasks' reviewer lists (client tasks used `code-reviewer` instead).
- **`server/internal/service/notifier_test.go`** is Phase 2 (Task 16) — out of scope for this
  audit; do not flag it as missing from Phase 1.

Write the audit report to
`/home/makar/PoshivOn/work/access-control/logs/working/task-12/test-audit-report.md`. Structure
it as: an overall verdict, then per-file findings (bullet coverage table or list: tech-spec
bullet → present/missing/weak → note), then the five load-bearing checks above as a dedicated
section, then a short list of concrete gaps if any (file, missing case, suggested fix). Do not
modify any test or source file — this is a report-only task.

There is no `go test -cover` convention established in this project (the only pre-existing test
file, `server/internal/service/costing_test.go`, has no coverage tooling wired into CI). This
audit is a manual read-through against the tech-spec's stated test list, not a coverage-percentage
check. Running `go test ./...` to confirm the suite currently passes is useful supporting evidence
but is not itself the audit.
