## Description

Deploy Phase 1 of the access-control feature to production and verify the deploy went cleanly
through logs. This is a pure deploy action — no code changes here, everything needed
(`.github/workflows/deploy.yml` with the `test` job wired via `uses:`/`needs:` from Task 9,
migration `004_access_control`, all backend/frontend changes) was already built and reviewed
in Waves 1–8 and passed Pre-deploy QA in Task 13.

The push of a version tag triggers `.github/workflows/deploy.yml`. Per Task 9's wiring, the
workflow now runs a `test` job first (`uses: ./.github/workflows/test.yml`), and
`build-and-deploy` only runs if `needs: test` succeeds — a failing test suite blocks the
deploy instead of shipping broken code. `build-and-deploy` then builds and pushes the `app`
and `web` images, and deploys via SSH to the production host running
`docker-compose.prod.yml` (`poshivon_app`, `poshivon_web`, `poshivon_proxy`, `poshivon_db`
containers).

On container start, `server/cmd/main.go` applies pending migrations automatically and
unconditionally, including `server/migrations/004_access_control.up.sql`. This is the
important part to watch: the migration step is not gated by any flag and there is no rollback
command — see Details below and the tech-spec Risks table entry for this deploy.

## What to do

- Push the release tag that triggers `.github/workflows/deploy.yml` (per the project's
  existing tagging convention).
- Watch the Actions run: confirm the `test` job completes successfully before
  `build-and-deploy` starts (the `needs: test` gate from Task 9).
- After `build-and-deploy` finishes, connect to the production host and inspect
  `docker compose logs app` for the startup window: confirm no migration failure message and
  no crash-loop (i.e., the container is not repeatedly restarting).
- Confirm the `004_access_control` migration is recorded as applied in `schema_migrations` on
  the production database.
- Confirm `app`, `web`, and `proxy` containers are all up and healthy (not restarting, not
  exited).
- If the migration step fails and the container is crash-looping, do **not** attempt an
  automated rollback — there isn't one. Follow the manual-recovery note in Details and involve
  the user before retrying.

## Details

The migration is **not reversible** — there are no down-migrations anywhere in this project
(`server/migrations/migrate.go` has no down-migration mechanism at all). It applies
automatically and unconditionally at container start
(`server/cmd/main.go` — `log.Fatalf` on migration error per lines 32-34). This means:

- If migration `004_access_control` fails on production, `poshivon_app` will crash-loop
  (repeatedly restart) instead of starting in a degraded/skip-migration mode.
- There is no automated or scripted rollback path. Recovery is a **manual database
  operation**: connect via `docker exec poshivon_db mariadb ...` and correct the schema state
  by hand (this is the mitigation recorded in tech-spec's Risks table for this exact
  scenario — "Миграция падает на проде — контейнер уходит в crash-loop, down-миграций нет").
- The migration was already verified against `mariadb:11.4` and confirmed idempotent during
  Task 1 (the migration-authoring task), so a crash on production would indicate an
  environment difference (schema drift, permissions, connectivity) rather than a bug in the
  SQL itself — investigate the actual DB state via `docker exec poshivon_db mariadb` before
  attempting any manual fix.
- Do not attempt to "fix forward" by editing the migration file after `004_access_control` is
  already recorded in `schema_migrations` — the version is fixed once applied; a new numbered
  migration would be required instead.

**Dependencies:** depends on Task 13 (Pre-deploy QA) having passed — this task only deploys
what QA has already approved. Relies on Task 9's CI wiring (`test` job gating
`build-and-deploy` via `needs:` in the same `deploy.yml` file) already being in place from
Wave 9.

**Edge cases:**
- Migration fails on production → crash-loop, no rollback command, manual DB intervention
  required (see above); do not proceed to Task 15 (Post-deploy verification) until resolved.
- `test` job fails → `build-and-deploy` must not run; if it somehow runs anyway, that is a CI
  configuration regression from Task 9 and should be reported before retrying the deploy.

`deploy-pipeline` skill's standard tag-push-and-observe-logs workflow for this project's
