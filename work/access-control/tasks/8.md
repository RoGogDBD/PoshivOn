# Task 8: Раздел «Пользователи» для администратора

## Required Skills

## Description

This is the last client-side task of Phase 1 (Wave 8, depends on Task 7). It gives the admin
role a working UI to grant and revoke access — closing US-7 through US-10 and US-12 from the
user-spec: an admin sees a list of every user who has ever logged in, each with an access
checkbox; toggling it grants or revokes access and the change persists; a non-admin does not
see this section at all.

By the time this task runs, Task 7 has already added the client-side access gate: a third call
in `Panel.jsx`'s bootstrap effect fetches `GET /api/v1/access/me` (response shape per tech-spec
Data Models / Contract API: `{login, display_name, email, role, has_access, request_status,
contact_email}`), stores the result (most likely in the existing `profile` state or a sibling
state variable — check what Task 7 actually named it), and gates the workspace behind
`has_access || role === 'admin'` with `AccessRequestBanner` shown otherwise. This task consumes
that already-fetched `role` field to conditionally render a third nav item and section — it does
not add a new fetch for identity, only for the admin user list.

`AdminUsersSection.jsx` is a new component that, when mounted, calls `GET /api/v1/admin/users`
(via a new function in `accessApi.js`, e.g. `fetchAdminUsers`) which returns `{items:[UserRecord]}`
— `UserRecord` per tech-spec `server/internal/service/access.go` has fields `Login`,
`DisplayName`, `Email`, `Role`, `HasAccess`, `RequestStatus`, `RequestedAt`, `CreatedAt` (exact
JSON key casing is whatever Task 5's handler actually emits — check `access.go`/`access_test.go`
from Task 5, it should follow the same snake_case convention already visible in the
`/api/v1/access/me` contract: `login`, `display_name`, `email`, `role`, `has_access`,
`request_status`). Each row renders a checkbox reflecting `has_access`; toggling it calls
`POST /api/v1/admin/users/{login}/access` with body `{"granted": bool}` (a new `setUserAccess`
function in `accessApi.js`) and, on success, updates that row's local state so the UI reflects
the change without a full refetch — but since Decision 15 says the app doesn't poll, a page
reload must also show the persisted value, which is what the acceptance criteria verify.

Decision 10 governs the admin's own row specifically: access is checked as `has_access ||
role == 'admin'` on the server, so the flag is irrelevant for an admin account — but the row
must still communicate that admin access can't be revoked through this UI. The admin's row is
rendered with its checkbox checked and non-interactive (`disabled`), for both the logged-in
admin's own row and the other admin's row — this is not "can't uncheck yourself", it's "can't
uncheck any admin", closing the "both admins lock themselves out" risk the user-spec flagged.
Determine "is this row an admin" from that row's own `role` field in the list response, not by
comparing `login` to the current session's login.

Today `Panel.jsx`'s nav (`Panel.jsx:561-576`) has exactly two `panel__link` buttons toggling
`activeSection` between `"workspace"` and `"settings"`, and the section body
(`Panel.jsx:617-853`) is a binary ternary: `activeSection === "settings" ? <settings-section> :
<workspace-section>`. Adding a third value (`"users"`) means this ternary can no longer express
the routing — it must become a chain of conditions (e.g. `activeSection === "settings" ? ... :
activeSection === "users" ? ... : ...`) or an equivalent if/else-if structure. The always-visible
`panel-summary` block (`Panel.jsx:599-615`, three cards: active chat, chat count, chat total) sits
above this ternary today, so it renders regardless of section — including on top of `settings`
already. Once a third `"users"` section is added, this block would render above it too unless it
is moved inside the workspace branch specifically, since chat-oriented summary cards make no
sense above a user-management table. Handle that move as part of this task.

This task is functional-only on styling: `AdminUsersSection.jsx` and the new nav item should use
plain, readable markup consistent enough not to look broken, but matching the rest of the panel's
visual language (`.panel__card`, `.panel-chat-list__item`, `.panel__notice`, `.panel__empty`
classes in `client/src/App.css`) is explicitly deferred to Phase 2 Task 17 (a separate,
later-executed phase) — don't over-invest in visual polish here.

## Details

**Files:**
- `client/src/components/AdminUsersSection.jsx` (new) — the users list component described
  above: fetch on mount via `accessApi.js`, render rows with checkboxes, disable+check admin
  rows per Decision 10, wire non-admin toggles to `setUserAccess`.
- `client/src/pages/Panel.jsx` (edit) — third conditional nav button; convert the
  `activeSection === "settings" ? ... : ...` ternary (currently binary, `Panel.jsx:617-853`) into
  a three-way structure covering `"settings"` / `"users"` / default `"workspace"`; move the
  `panel-summary` block (`:599-615`) inside the workspace branch.
- `client/src/utils/accessApi.js` (edit, only if Task 7 didn't already cover this) — add
  `fetchAdminUsers` (`GET /api/v1/admin/users`) and `setUserAccess(login, granted)` (`POST
  /api/v1/admin/users/{login}/access`, body `{"granted": granted}`), following the existing
  `request()` wrapper pattern from `panelApi.js` (auth-aware fetch, JSON error unwrapping,
  `error.status` set from the response).

**Dependencies:** Task 7 (client access gate, `accessApi.js` scaffold, bootstrap effect that
fetches `/api/v1/access/me` and stores `role`) must land first — this task reads that state
rather than fetching identity itself. Also implicitly depends on the server-side Task 5
(`AccessHandler`, the four access/admin routes) being functional, since this task's manual
verification exercises the real endpoints against a running server.

**Edge cases:**
- Admin toggling their own (or the other admin's) checkbox must be impossible client-side
  (`disabled`) — the server does **not** reject this call for an admin target: `RequireAdmin`
  only checks the caller's role, not who the target `{login}` is, so a `POST
  /api/v1/admin/users/{admin-login}/access` from an admin caller succeeds server-side against
  any admin row, including their own (see tasks/2.md/5.md — `SetAccess` has no target-is-admin
  guard). The client `disabled` state is the *only* guard against ever sending that request.
  Decision 10 is what makes a stray flip harmless if it somehow gets sent anyway (access is
  `has_access || role == 'admin'`, so the flag itself doesn't gate an admin) — it is not a
  server-side rejection.
- Empty list edge case is not realistic here — the seed migration (Task 1) always creates at
  least the two admin rows, so `GET /api/v1/admin/users` never returns an empty `items` array in
  practice; no special empty-state design effort needed beyond not crashing on `items: []`.
- A user with `request_status: "pending"` but `has_access: false` still appears as an unchecked,
  interactive row like any other non-admin user — this task does not need to surface
  `request_status` distinctly in the UI (no acceptance criterion requires it); if included, keep
  it a simple text label, not a separate approve/reject flow (that's not in scope — the toggle
  itself is the approve/reject mechanism per tech-spec's "Админские операции").
- Toggle failure (network error, 403, 404) must not silently leave the checkbox in the
  optimistic-but-wrong state — either wait for the response before flipping local state, or
  revert on error.

**Implementation hints:**
- Match `accessApi.js`'s existing `request()`-wrapper style from `panelApi.js` (import
  `authFetch`, unwrap JSON error bodies, throw with `error.status` set) rather than introducing a
  second fetch pattern — check what Task 7 already established in `accessApi.js` before writing
  new functions.
- The three-way section switch in `Panel.jsx` can be a nested ternary matching the existing
  code's style, or refactored to an if/else-returning variable computed just above the JSX
  return — either is acceptable as long as `panel-summary` ends up strictly inside the
  `"workspace"` branch and not shared across branches.
