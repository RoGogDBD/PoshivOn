# Task 15: Post-deploy verification

## Required Skills

Before starting, load:
- `/skill:post-deploy-qa` — [skills/post-deploy-qa/SKILL.md](~/.claude/skills/post-deploy-qa/SKILL.md)

## Description

This task is the Agent Verification Plan (AVP) from tech-spec.md, executed against the live,
deployed production environment instead of a local dev environment. It runs after Task 14
(Deploy) has shipped the access-control feature to prod behind nginx on `poshivon.ru`.

The access-control feature introduces roles (`admin`/regular user), an access-request flow,
and admin-only user management. This task confirms that everything the feature depends on
actually holds true on the live system: the migration applied cleanly and left exactly two
admins in the database, the HTTP contract (401/403/404 on the right endpoints) is enforced
through the real prod nginx (not just in local tests), `/auth/refresh` reaches the Go backend
rather than being swallowed by the SPA's catch-all route, and the panel UI renders the correct
state (access banner, admin section, or neither) for each of the three user roles.

Verifying actual SMTP email delivery to admins (US-5) and the visual polish of the banner/admin
section are explicitly out of scope here — see Details below.

## What to do

1. Confirm the deployed container `poshivon_app` is healthy and the `004_access_control`
   migration applied without leaving the app in a crash-loop; confirm the admin count in the
   live database is exactly 2.
2. Run the curl-based HTTP contract checks against the real prod host through nginx: anonymous
   access to `/api/v1/access/me` and `/api/v1/users/chats` returns 401; a session without access
   gets 403 on `/api/v1/users/chats`; a non-admin session gets 403 on `/api/v1/admin/users`; the
   removed OAuth-token route `POST /auth/yandex` returns 404; `POST /auth/refresh` returns a
   JSON response from the Go backend, not the SPA's HTML shell.
3. Drive the deployed panel with Playwright MCP as three different users (no access, regular
   access, admin) and confirm each sees the correct UI: access banner only, panel without the
   "Пользователи" section, panel with the "Пользователи" section.
4. Record results and report them per the post-deploy-qa skill's reporting format; do not fix
   code from this task — if something fails, report it as a finding for a follow-up task.

## Verification Steps

This task's entire content is its verification checklist — there is no separate
"implementation" to verify; the checks below ARE the deliverable.

### Smoke

- `docker compose -f docker-compose.prod.yml logs poshivon_app --tail 100` (or the prod
  equivalent used by Task 14's deploy) → no repeated restarts / crash-loop, migration log line
  for `004_access_control` present
- `docker exec poshivon_db mariadb -uroot -p"$MARIADB_ROOT_PASSWORD" poshivon -e "SELECT COUNT(*) FROM users WHERE role='admin';"` → returns `2`
- `curl -i https://poshivon.ru/api/v1/access/me` (no cookies) → `HTTP/1.1 401`
- `curl -i https://poshivon.ru/api/v1/users/chats` (no cookies) → `HTTP/1.1 401`
- `curl -i -b "session=<cookie of a logged-in user without access>" https://poshivon.ru/api/v1/users/chats` → `HTTP/1.1 403`
- `curl -i -b "session=<cookie of a logged-in non-admin user>" https://poshivon.ru/api/v1/admin/users` → `HTTP/1.1 403`
- `curl -i -X POST https://poshivon.ru/auth/yandex` → `HTTP/1.1 404`
- `curl -i -X POST https://poshivon.ru/auth/refresh` → response `Content-Type: application/json` (or backend error JSON body), not the SPA's `text/html` shell — confirms nginx proxies `/auth/refresh` to `app`, per Task 14's nginx change

### User

- Playwright MCP: open `https://poshivon.ru/panel` as a user who has not been granted access →
  confirm the access-request banner is rendered (with the `CONTACT_EMAIL` contact text) and no
  working panel UI (chats/settings/calculations) is visible
- Playwright MCP: open `https://poshivon.ru/panel` as one of the two live administrators →
  confirm the "Пользователи" section is visible in navigation, with the user list rendered
- Playwright MCP: open `https://poshivon.ru/panel` as a regular user who has been granted
  access (not an admin) → confirm neither the access banner nor the "Пользователи" section
  is present, and the normal panel UI works

## Details

**Files:** none — this is a live-environment verification task, no code files are modified
or read as part of executing it.

**Dependencies:** Task 14 (Deploy) must have completed successfully before this task runs;
this task verifies the state Task 14 produced on the live host `poshivon.ru`.

**Tools required:** `curl`, `bash` (+ `docker compose` / `docker exec` against the prod host
or through SSH to it), Playwright MCP — per tech-spec's Agent Verification Plan → Tools
required.

**Test accounts needed:** a session cookie (or live login flow) for each of the three roles
under test — an admin, a regular user with access, and a user without access — obtained by
logging in through the real Yandex OAuth flow against prod, since the OAuth-token bypass
route (`POST /auth/yandex`) has been removed by this feature.

**Out of scope for this task (explicitly deferred to Phase 2):**
- Verifying actual email delivery to administrators on new access requests (US-5) — Phase 1
  ships without SMTP by design; the banner shows a static `CONTACT_EMAIL` value instead of
  triggering a notification. Email delivery becomes verifiable once Phase 2's Task 16
  (`SMTPNotifier`) ships, and will be checked by Phase 2's own post-deploy task (Task 20, to
  be created in a later `/decompose-tech-spec` run once Phase 2 is decomposed).
- Visual polish of the access banner and admin "Пользователи" section — Phase 1 ships these
  functionally without styling (Phase 2's Task 17 applies `.panel__card` / `.panel__notice`
  styling); this task only checks that the correct section renders for the correct role, not
  how it looks.

**Edge cases:**
- If the admin count is not exactly 2, do not attempt to fix the database from this task —
  report it as a blocking finding; the two admin logins are user-provided (per user-spec.md
  "User verifies") and only the user can confirm they are correct.
- If `/auth/refresh` still returns the SPA's HTML instead of backend JSON, this indicates
  Task 14's nginx proxy change did not take effect on the live host (config not reloaded,
  wrong compose file deployed, etc.) — report as a blocking finding rather than editing nginx
  config directly from this task.
