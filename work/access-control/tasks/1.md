## Required Skills

## Description

Создать `server/migrations/004_access_control.up.sql` — фундамент всей фичи «доступ к
панели по заявке с одобрением администратором». Миграция добавляет:

- на `users`: `role`, `has_access`, `email`, `display_name` — состояние доступа и роли,
  проверяемое сервером на каждом запросе (см. Solution, пункт 2 и Decision 3);
- на `oauth_sessions`: `yandex_login`, `yandex_email`, `yandex_display_name` — личность
  сессии сохраняется при входе, а не запрашивается у Яндекса на каждый вызов (Decision 1);
- таблицу `access_requests` — одна строка заявки на пользователя с upsert-семантикой
  (Decision 5);
- сидирование двух администраторов (`RoGogDBD`, `irina2000aleshina`) через
  `INSERT ... ON DUPLICATE KEY UPDATE` — создаёт строку `users`, даже если аккаунт ни разу
  не входил, и назначает роль независимо от истории входа (Decision 4, и подробное
  обоснование в Data Models).

Без этой миграции ни один из последующих серверных и клиентских тасков (доменный сервис,
middleware, репозитории, обработчики) не может быть реализован — она открывает Wave 1 и
не имеет зависимостей.

  SQL-блоком):
  - `ALTER TABLE users ADD COLUMN IF NOT EXISTS ...` — `role`, `has_access`, `email`,
    `display_name`, плюс `ADD CONSTRAINT IF NOT EXISTS chk_users_role CHECK (role IN

  - `ALTER TABLE oauth_sessions ADD COLUMN IF NOT EXISTS ...` — `yandex_login`,
    `yandex_email`, `yandex_display_name`.
  - `CREATE TABLE IF NOT EXISTS access_requests (...)` — `user_id` как PRIMARY KEY,
    `status`, `created_at`, `decided_at`, `decided_by`, FK на `users(id) ON DELETE CASCADE`,
    CHECK на `status`.
  - `CREATE INDEX IF NOT EXISTS idx_users_role_has_access ON users(role, has_access);`.
  - `INSERT INTO users (id, role, has_access) VALUES (...) ON DUPLICATE KEY UPDATE role =
    'admin';` для `RoGogDBD` и `irina2000aleshina`.

- Не создавать down-миграцию — в проекте их нет.
- Убедиться, что каждый оператор идемпотентен (`IF NOT EXISTS` на колонках, констрейнтах,
  индексах и таблице; upsert на INSERT), чтобы повторный прогон того же файла не падал и не
  дублировал строки администраторов.

## Details

**Files:**
- `server/migrations/004_access_control.up.sql` (новый) — создать со следующим содержимым,
  скопированным дословно из раздела Data Models тех-спека:

```sql
ALTER TABLE users
  ADD COLUMN IF NOT EXISTS role VARCHAR(16) NOT NULL DEFAULT 'user',
  ADD COLUMN IF NOT EXISTS has_access BOOLEAN NOT NULL DEFAULT FALSE,
  ADD COLUMN IF NOT EXISTS email VARCHAR(255) NULL,
  ADD COLUMN IF NOT EXISTS display_name VARCHAR(255) NULL,
  ADD CONSTRAINT IF NOT EXISTS chk_users_role CHECK (role IN ('user','admin'));

ALTER TABLE oauth_sessions
  ADD COLUMN IF NOT EXISTS yandex_login VARCHAR(255) NULL,
  ADD COLUMN IF NOT EXISTS yandex_email VARCHAR(255) NULL,
  ADD COLUMN IF NOT EXISTS yandex_display_name VARCHAR(255) NULL;

CREATE TABLE IF NOT EXISTS access_requests (
    user_id     VARCHAR(255)  NOT NULL PRIMARY KEY,
    status      VARCHAR(16)   NOT NULL DEFAULT 'pending',
    created_at  TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    decided_at  TIMESTAMP     NULL,
    decided_by  VARCHAR(255)  NULL,
    CONSTRAINT fk_access_requests_user
        FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
    CONSTRAINT chk_access_requests_status
        CHECK (status IN ('pending','approved','rejected'))
);

CREATE INDEX IF NOT EXISTS idx_users_role_has_access ON users(role, has_access);

INSERT INTO users (id, role, has_access) VALUES
  ('RoGogDBD', 'admin', TRUE),
  ('irina2000aleshina', 'admin', TRUE)
ON DUPLICATE KEY UPDATE role = 'admin';
```

Прочие файлы в задаче не меняются — она затрагивает только миграцию.

**Почему именно `INSERT ... ON DUPLICATE KEY UPDATE`, а не `UPDATE`:** у аккаунта, ещё ни
разу не входившего в систему, строки `users` не существует, и `UPDATE` его бы не затронул.
`INSERT ... ON DUPLICATE KEY UPDATE` создаёт строку сразу и назначает роль независимо от
того, входил администратор или нет, а у уже существующей строки меняет только `role`. При
последующем входе `EnsureUser` обновляет лишь `email` и `display_name` (Decision 11),
поэтому роль переживает вход. Ручного шага после выкатки не требуется.

Оба логина (`RoGogDBD`, `irina2000aleshina`) жёстко закодированы намеренно: миграция
применяется автоматически при старте контейнера (`server/cmd/main.go:32-34`) и необратима —
версия фиксируется в `schema_migrations`, а down-миграций в проекте нет. Правка файла после
того, как эта версия уже применена хоть на одном окружении, не удалит и не изменит посеянные
строки; исправление такой ошибки — ручная операция в БД, а не повторный прогон миграции.

**Load-bearing именование файла:** трёхзначный числовой префикс `004` обязателен — порядок
применения миграций определяется лексикографической сортировкой имён файлов
(`server/migrations/migrate.go:25`, `sort.Strings(entries)`). Файл должен называться ровно
`004_access_control.up.sql`, чтобы применяться после `003_pricing_and_chat_delete.up.sql` и
попасть в `embed.FS` через паттерн `*.up.sql` (`migrate.go:14`).

**Как файл применяется:** весь файл выполняется одним вызовом `db.Exec(string(sqlBytes))`
(`server/migrations/migrate.go:43`) — это работает только благодаря `multiStatements=true`
в DSN (`server/internal/db/db.go:63`, `buildDSN`). Многострочный SQL с несколькими
`ALTER TABLE` / `CREATE TABLE` / `CREATE INDEX` / `INSERT` в одном файле — стандартный
паттерн для этого проекта (см. `002_costing_schema.up.sql`, `003_pricing_and_chat_delete.up.sql`).
Down-миграций в проекте нет и для этого файла заводить не нужно.

**Dependencies:** нет зависимостей от других тасков — это первая задача Wave 1, фундамент
для Task 2 (`AccessService`) и последующих задач, которые опираются на новые колонки и
таблицу.

**Edge cases:**
- Повторный прогон того же файла (например, при переразвёртывании контейнера с уже
  применённой версией в `schema_migrations` миграция просто не перезапускается движком
  `migrate.go`, но задача также обязана быть безопасной при ручном повторном прогоне через
  `mariadb`-клиент — отсюда требование идемпотентности каждого оператора).
- MariaDB 11.4 поддерживает `IF NOT EXISTS` для `ADD COLUMN`, `ADD CONSTRAINT` и
  `CREATE INDEX` — не более старую семантику, где это может быть недоступно; версия
  фиксирована тех-спеком, дополнительно проверять совместимость с другими версиями не нужно.
- Администратор, ещё не входивший в систему (нет строки `users`) — `INSERT ... ON DUPLICATE
  KEY UPDATE` создаёт строку с `role='admin', has_access=TRUE`.
- Администратор, уже имеющий строку `users` с `role='user'` (входил до миграции) — оператор
  меняет только `role`, `has_access` в UPDATE-ветке не участвует (см. точный текст
  `ON DUPLICATE KEY UPDATE role = 'admin'` — не трогает `has_access`).

**Implementation hints:**
- Стиль CHECK-констрейнтов и `VARCHAR` вместо `ENUM` — консистентность с
  `market_status VARCHAR(64)` в `003_pricing_and_chat_delete.up.sql:16` и
  CHECK-констрейнтами в `002_costing_schema.up.sql:46-53` (Decision 4).
- Порядок операторов внутри файла не строго регламентирован тех-спеком, но логичен:
  сначала `ALTER TABLE users`, затем `ALTER TABLE oauth_sessions`, затем `CREATE TABLE
  access_requests` (зависит от `users` через FK), затем индекс, затем seed-`INSERT`
  (зависит от готовой таблицы `users` с колонкой `role`).
