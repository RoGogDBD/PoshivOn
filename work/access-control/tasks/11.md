# Task 11: Security Audit

## Description

This is the Audit Wave of the feature "Доступ к панели по заявке с одобрением
администратором" (access-control) — a full-feature security audit across everything built
in Phase 1 MVP (Tasks 1-9), after all nine tasks are complete and merged. It is report-only:
no code changes.

The feature rewrites the entire authorization model of the product: identity moves into the
session row, access becomes a database-backed flag checked on every request, a new admin
surface is introduced, and a known unauthenticated login bypass is removed. Every one of
these changes touches trust boundaries — session handling, origin checking, role
determination, ownership resolution for existing data routes. Tasks 1-9 were each reviewed
individually by `security-auditor` as part of their own review cycle, but no task saw the
full picture: how the migration's seeded roles interact with `EnsureUser`'s upsert, how
`RequireSameOrigin` composes with the OAuth code exchange, how the client's gating logic
lines up with what the server actually enforces. This task is that full-picture pass.

The tech-spec's own history matters here: two prior security-auditor passes on the *design*
(before any code existed) found and forced closure of concrete vulnerabilities — broken
access control on `/api/v1/users/*` (owner taken from the URL, not the session), the
unauthenticated `POST /auth/yandex` token-login endpoint (silently grants admin role after
this feature), login CSRF via a missing `Origin` check on `/auth/yandex/code`, anonymous
role-injection via a shared GORM model (`userModel` gaining a `Role` column would let any
authenticated write reset it), verbose error-text leakage through `writeAPIDomainError`, and
Prometheus cardinality abuse via an unauthenticated `{login}` path segment recorded before
authorization runs. Decisions 1, 2, 6, 7, 8, 9, 10, 11, 13, 17, 18 in the tech-spec are the
design-level closures for exactly these findings. The design was verified sound — this audit
verifies that the **code**, as actually implemented across Tasks 1-9, does what those
decisions say it does. A decision can be correct on paper and still not survive contact with
implementation (a middleware ordering slip, a forgotten route registration, a field that
silently didn't make it into the SELECT).

## What to do

- Read every file touched by Tasks 1-9 (full list in Context Files below) — server (Go) and
  client (React/Vite) — as one connected system, not as nine independent diffs.
- Run a standard OWASP Top 10 pass across all of it: injection (SQL via GORM/`database/sql`),
  broken access control, authentication/session handling, security misconfiguration
  (CORS/Origin, cookies, SMTP-adjacent config even though Task 16 is Phase 2 and out of
  scope), SSRF, insecure design, logging/monitoring gaps, cryptography (session tokens,
  refresh tokens), and known-vulnerable patterns.
- Trace the auth/data flow across component boundaries specifically — not just within a
  single file:
  - Session creation (`HandleYandexCode`) → identity persisted on `oauth_sessions` →
    `RequireAuth` reading it back → `RequireAccess`/`RequireAdmin` deciding on DB state →
    handler using `context` identity, never a URL/body-supplied owner.
  - Token rotation (`HandleRefresh` / `UpdateSessionTokens`) → does identity survive, or does
    a rotation silently drop `yandex_login` and downgrade the session to
    `session_identity_missing`.
  - `EnsureUser` on every login → does its `INSERT ... ON DUPLICATE KEY UPDATE` column list
    stay restricted to `email`/`display_name` only, never touching `role`/`has_access`
    (Decision 11's invariant — the admin-demotion regression: get this wrong and both admins
    lose their role on next login) — check this on the actual `PostgresRepository`
    implementation, not just the interface. Separately, confirm the shared `userModel` struct
    (`postgres.go`) itself was never extended with a `Role`/`HasAccess` field in the first
    place (Decision 13's invariant — a distinct check: this one is about the GORM model's
    shape, not about what `EnsureUser`'s SQL updates).
  - `RequireSameOrigin` → is it actually wired onto every mutating route from the tech-spec's
    middleware table (`/api/v1/*`, `POST /auth/yandex/code`, `POST /auth/refresh`,
    `POST /auth/logout`), in the correct order relative to `RequireAuth`/`RequireAccess`, and
    does the empty-`CORS_ALLOWED_ORIGINS` path fail closed (same-origin fallback) rather than
    fail open.
  - `writeAPIDomainError` → does every branch (400/403/404/409/429/500/503/504) return fixed
    category text with the real error only in the log, on every call site, not just the new
    403/409 branches.
  - `normalizePath` in metrics → does the `{login}` segment after `/admin/users/` collapse
    regardless of form, and does this happen before or doesn't matter relative to
    authorization (the label is written either way — verify the collapse itself, not that
    auth runs first).
  - Client gating (`Panel.jsx` bootstrap effect, data-loading effects) → does an
    unauthenticated/no-access user's browser actually never issue `/settings`, `/chats`,
    `/calculations` requests, or does the client only *hide UI* while still firing requests
    the server happens to reject.
  - `POST /auth/yandex` and `HandleYandexLogin` → confirm actual removal (route unregistered
    in `main.go`, handler deleted), not just deprecation.
- For each of Decisions 1, 2, 6, 7, 8, 9, 10, 11, 13, 17, 18: state explicitly whether the merged
  code implements what the decision specifies, and if not, exactly where it diverges (file,
  function, what's missing or wrong).
- Check for issues that only exist because multiple tasks' outputs combine — e.g. a route
  registered in Task 5's `main.go` wiring that Task 6's `http.go` rewrite might have
  bypassed, or a client call in Task 7/8 hitting an address Task 6 changed.
- Write the audit report. No code changes, no fixes — findings only, with file:line
  references and severity (Critical/High/Medium/Low per the security-auditor skill's scale).
- Save the report under `work/access-control/logs/working/task-11/` (see Details for the
  exact convention) and summarize it in `decisions.md` per Post-completion.

## Details

**Files:** none modified — report-only. Report written to
`work/access-control/logs/working/task-11/` — follow the same convention the per-task
reviewer JSON reports use elsewhere in this feature (see Reviewers sections of Tasks 1-9,
e.g. `work/access-control/logs/working/task-1/security-auditor-1.json`), so the report sits
alongside the rest of this feature's review artifacts and `decisions.md` can link to it.

**Dependencies:** all of Wave 1-9 (Tasks 1-9) must be `status: done` before this task starts
— it audits the merged result, not any single task's diff. This task has no code
dependencies of its own to build on; it only reads.

**Edge cases:**

**Scope boundary — what NOT to flag (already accepted, tracked in tech-spec Risks table):**
- `ya_access` / `yandex_refresh_token` stored in plaintext in `oauth_sessions` — pre-existing,
  explicitly out of scope, decoupling session from upstream token is a separate refactor.
- `redirect_uri` in `HandleYandexCode` taken from request body rather than only from config —
  pre-existing, Yandex validates it server-side on token exchange, this feature doesn't touch
  it.
- No path to demote an admin via API/UI — intentional per user-spec (exactly two fixed
  admins), not a gap.
- SMTP notifier (`server/internal/service/notifier.go`) and its wiring — Phase 2 / Task 16,
  not yet built, out of scope for this audit.
- Layout/styling of the banner and admin section (Task 17, Phase 2) — not a security concern
  and out of scope regardless.

These are risks the tech-spec already named and the user accepted — re-flagging them without
new information adds noise, not signal. If this audit finds something *new* that makes an
already-accepted risk worse (e.g. Decision 12's wider OAuth scope increasing the value of a
leaked `ya_access` token — the tech-spec Risks table already calls this out explicitly),
note the connection, don't just repeat the existing entry.

**What IS in scope even though it looks like "config":** `CORS_ALLOWED_ORIGINS`'s presence
or absence on prod (Decision 8's same-origin fallback depends on getting this right),
whether SMTP-shaped secrets could leak through Task 9's compose/workflow changes ahead of
Phase 2, whether `/auth/refresh` proxying changes in `client/nginx.conf` accidentally widen
what's reachable.

**Implementation hints (where to look for each decision, not exhaustive):**
- Decision 1/2 (identity in session, old sessions rejected): `auth/store.go` schema/read
  path, `RequireAuth` in `middleware.go` for the `session_identity_missing` branch.
- Decision 6 (uniform `/api/v1/*` gating, owner from context not URL): `main.go` route
  wiring, `http.go` handlers reading owner — grep for anywhere a handler still reads a
  path/body-supplied user identifier.
- Decision 7 (token-login endpoint removed): `main.go` registration list, absence of
  `HandleYandexLogin` in `handler/auth.go`, absence of the implicit branch in
  `AuthCallback.jsx`.
- Decision 8 (Origin check, fail-closed on empty allowlist): `RequireSameOrigin` in
  `middleware.go`, and its actual attachment points in `main.go` — check it's on
  `POST /auth/yandex/code` too, not just `/api/v1/*`.
- Decision 9 (OAuth `state`): `yandexAuth.js` generation/storage, `AuthCallback.jsx`
  comparison before code exchange.
- Decision 10 (admin bypasses `has_access`): `access.go` service-layer check — must be
  `has_access || role == 'admin'`, not `has_access` alone gated by a separate admin branch
  that could be bypassed.
- Decision 11 (`EnsureUser` never resets `role`/`has_access`): `postgres.go`'s `EnsureUser`
  implementation — the upsert's column list on conflict must be limited to `email`/
  `display_name`; a broader update (or a naive `Save`) would silently demote both admins on
  their next login.
- Decision 13 (`userModel` unchanged, access columns on a separate model): `postgres.go` —
  confirm `userModel` still has only `ID`/`CreatedAt`, and the three existing `upsertUser`
  call sites weren't touched to include access columns.
- Decision 17 (fixed error text, no leakage): every branch of `writeAPIDomainError` in
  `http.go`.
- Decision 18 (`{login}` collapsed in metrics before it can become a label): `normalizePath`
  in `metrics.go`.
