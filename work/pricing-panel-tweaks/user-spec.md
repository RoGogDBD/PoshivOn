# User Spec: pricing-panel-tweaks

## What we're building
На странице poshivon.ru/panel (раздел «Настройки» ценового калькулятора) меняем
порядок и названия тарифных режимов, переименовываем одну надпись, и добавляем
возможность добавлять и удалять строки в трёх списках (Изделия, Усложнения,
Скидки за количество). Задача поставляется двумя независимыми инкрементами:
(1) переименование/порядок/надпись — тривиальная правка, деплоится сразу;
(2) добавление и удаление строк — более объёмная часть с валидацией, деплоится
отдельно.

## Why
Текущие названия тарифов («Шедевр», «По быстрому») и их порядок не отражают
то, как их хочет видеть админ. Кроме того, в панели сейчас нет способа
добавить новое изделие, усложнение или диапазон скидки — список ограничен тем,
что было изначально задано в коде/сохранено ранее. Админу нужно расширять эти
списки самостоятельно, без правки кода.

## How it should work

### Инкремент 1 — переименование, порядок, надпись (Size S)
1. Админ открывает poshivon.ru/panel → «Настройки».
2. В переключателе режима калькулятора видит режимы в новом порядке: сначала
   «Продвинутый» (бывший «Шедевр»), затем «Быстрый» (бывший «По быстрому»).
   Внутренние значения режимов (`masterpiece`/`quick`), от которых зависит
   расчёт цены и хранение данных, не меняются — меняется только видимый текст.
3. Надпись «Скидки по партиям» везде на экране заменяется на «Скидки за
   количество» (в коде название хранится во множественном числе).

### Инкремент 2 — добавление и удаление строк (Size M)
4. В блоке «Изделия» админ видит кнопку «Добавить» → нажимает → открывается
   **одна форма со всеми полями изделия сразу** (Название, Мин. цена / шт,
   База, мин, Коэфф. сложности) — независимо от того, какой режим калькулятора
   сейчас активен. Все поля обязательны и валидируются на клиенте перед
   добавлением (см. Constraints). Никаких скрытых полей и дефолтов, которые
   пользователь не видит.
5. Аналогично в блоке «Усложнения»/«Операции» — одна форма со всеми полями
   (Название, Надбавка %, Доп. минуты, Доп. материал/шт), и в блоке «Скидки за
   количество» — форма (мин. кол-во, макс. кол-во, процент скидки).
6. Ровно 3 кнопки «Добавить» на экране — по одной на блок, видны независимо от
   активного режима калькулятора (не дублируются на каждый режим).
7. Рядом с каждой существующей и новой строкой в 3 блоках — кнопка «Удалить»,
   убирающая строку из списка на экране (для Изделий/Усложнений — удаление
   ключа из map по имени; для Скидок — удаление элемента массива по индексу).
8. Админ нажимает существующую кнопку «Сохранить изменения» — весь набор
   настроек, включая добавленные/удалённые строки, сохраняется на сервере
   одним запросом.
9. После перезагрузки страницы все изменения (добавления и удаления) остаются
   в силе.
10. Если админ пытается добавить изделие/усложнение с именем, которое уже
    есть в списке (сравнение без учёта регистра, с обрезкой пробелов по
    краям), форма показывает ошибку «Такое название уже есть» и не даёт
    добавить дубликат.

## Acceptance Criteria

Инкремент 1:
- [ ] Порядок тарифных режимов на /panel изменён: бывший второй режим теперь
      показывается первым.
- [ ] Названия режимов — «Продвинутый» и «Быстрый»; внутренние значения
      (`masterpiece`/`quick`) в коде, БД и расчётах не изменены.
- [ ] Надпись «Скидки по партиям» заменена на «Скидки за количество» везде,
      где отображается (общий компонент для обоих режимов).

Инкремент 2:
- [ ] Ровно 3 кнопки «Добавить» на экране: у Изделий, у Усложнений/Операций и
      у Скидок за количество — каждая видна независимо от активного режима
      калькулятора (не дублируется на каждый режим).
- [ ] Форма добавления изделия/операции показывает все поля сразу (не только
      поля активного режима) и требует их заполнения — новая строка не
      получает скрытых/фиктивных значений по умолчанию для полей, которые
      пользователь не видел.
- [ ] Добавление строки в любом из 3 блоков + нажатие «Сохранить изменения» →
      строка сохраняется и остаётся после перезагрузки страницы; изделие,
      добавленное так, корректно считается ценой в обоих режимах калькулятора.
- [ ] Добавление строки в блок «Скидки за количество» с корректным диапазоном
      (мин/макс количество, процент) не приводит к ошибке сохранения; форма
      по умолчанию предлагает следующий диапазон, продолжающий последний
      существующий тир (min_qty = max_qty последнего тира + 1).
- [ ] Попытка добавить изделие/усложнение с именем, которое уже есть в
      списке (без учёта регистра и пробелов по краям), блокируется на клиенте
      с ошибкой «Такое название уже есть» — форма не даёт отправить, запись
      не перезаписывается молча.
- [ ] Кнопка «Удалить» рядом с любой строкой во всех 3 блоках убирает строку
      из списка; после «Сохранить изменения» и перезагрузки страницы строка
      отсутствует.

## Constraints
- Это **live продакшн-панель** — изменения не должны сломать уже сохранённые
  данные (существующие изделия, усложнения, скидки, значения тарифов).
- Переименование меток тарифов должно менять только отображаемый текст
  (`label`), не трогая внутренний ключ (`value: "masterpiece"/"quick"`), от
  которого зависит расчёт цены и хранение результатов расчётов.
- Настройки (изделия/усложнения/скидки) хранятся **на пользователя** — у
  каждого аккаунта с доступом к панели свой независимый набор данных, это не
  единый общий прайс-лист сайта. Новая строка появляется только в настройках
  того, кто её добавил — это ожидаемое, не побочное поведение.
- Backend требует для каждого изделия `base_minutes > 0` и
  `complexity_coeff > 0`, а для быстрого расчёта — `quick_price > 0`
  (иначе расчёт цены в быстром режиме падает с ошибкой для этого изделия,
  даже если сохранение прошло успешно). Форма добавления изделия собирает
  **все** эти поля сразу, поэтому скрытых дефолтов не требуется — это и
  исключает данный риск.
- Backend для «Скидки за количество» требует `MinQty > 0`,
  `MaxQty >= MinQty`, `0 <= Percent <= 100` — форма добавления должна
  предлагать валидный диапазон по умолчанию (продолжающий последний
  существующий тир), иначе попытка сохранить пустую/нулевую строку
  заблокирует сохранение **всех** настроек, включая несвязанные правки,
  сделанные в той же сессии (сохранение идёт одним запросом на весь объект).
- Строка в списке Изделий/Усложнений идентифицируется по имени (ключ map) —
  дублирующее имя нельзя допускать на клиенте, backend такую проверку не
  делает.
- Удаление строки — обратная операция к добавлению: убрать ключ из map /
  элемент из массива в локальном состоянии, персистится тем же способом
  (существующая кнопка «Сохранить изменения»), новый эндпоинт не нужен.
- Никаких новых бэкенд-эндпоинтов не требуется вообще: сохранение уже идёт
  одним запросом (весь объект настроек) через существующую кнопку
  «Сохранить изменения».
- На клиенте нет тестовой инфраструктуры (нет vitest/jest, нет ни одного
  `*.test.*` файла) — поднимать её в рамках этой задачи не будем (см.
  Testing).

## Risks
- **Риск:** Переименование меток тарифов может задеть места, где название
  используется как идентификатор. **Mitigation:** проверено в коде — «Шедевр»/
  «По быстрому» встречаются только как текст (`label`), реальный ключ везде —
  `masterpiece`/`quick`; правится только текстовое поле.
- **Риск:** Изначально рассматривался вариант с формой добавления, показывающей
  только поля активного режима, и скрытыми дефолтами для остальных — это могло
  привести к изделию с `quick_price = 0`, которое проходит сохранение, но потом
  роняет расчёт цены в быстром режиме. **Mitigation:** решение изменено — форма
  добавления всегда собирает все поля изделия/операции сразу, скрытых
  дефолтов нет вообще, риск снят архитектурно.
- **Риск:** Изделия/усложнения — это map по имени без проверки дублей на
  backend'е; добавление строки с существующим именем тихо перезапишет старую
  запись. **Mitigation:** проверка на дубликат имени (без учёта регистра и
  пробелов) добавлена на клиенте перед отправкой формы.
- **Риск:** Пустая/нулевая новая строка в «Скидки за количество» блокирует
  сохранение всех настроек целиком, а не только новой строки.
  **Mitigation:** форма подставляет валидный диапазон по умолчанию,
  продолжающий последний тир, и валидирует ввод на клиенте перед сохранением.
- **Риск:** Без unit-тестов новая клиентская логика (дедуп, валидация,
  дефолты диапазона скидок) может содержать баги, не пойманные до ручной
  проверки. **Mitigation:** осознанное решение — поднимать тестовую
  инфраструктуру клиента ради этой задачи не будем; полагаемся на ручную
  проверку по чек-листу в How to Verify.

## Technical Decisions
- Переименование затрагивает только отображаемый текст меток режимов и их
  порядок — внутренний ключ режима, от которого зависит расчёт и хранение
  данных, не меняется.
- Отдельного запроса на добавление/удаление строки нет — изменение попадает в
  локальное состояние формы и сохраняется вместе со всеми остальными полями
  через уже существующую кнопку «Сохранить изменения» (один запрос на весь
  объект настроек, как сейчас для всех прочих полей). Автосохранение не
  вводим — это был бы новый паттерн, не используемый больше нигде в панели.
- Форма добавления изделия/операции всегда показывает полный набор полей,
  независимо от активного режима калькулятора — это проще в реализации (одна
  форма вместо двух вариантов на блок) и убирает целый класс багов со
  скрытыми/фиктивными значениями по умолчанию, попадающими в реальный расчёт
  цены.
- Удаление строки — операция, симметричная добавлению: убирает
  строку/элемент из локального состояния, персистится тем же сохранением.
- Проверка на дубликат имени (без учёта регистра, с обрезкой пробелов)
  выполняется на клиенте — backend её не делает.
- Тестовая инфраструктура на клиенте не поднимается ради этой задачи —
  покрытие только ручной проверкой (см. Testing).
- Модель «настройки на пользователя» — существующее и осознанное поведение
  системы, менять её в рамках этой задачи не будем.
- Задача поставляется двумя независимыми инкрементами (см. What we're
  building) — так безобидное переименование не ждёт готовности более
  объёмной части с добавлением/удалением строк.

## Testing

**Unit tests:** на клиенте нет тестовой инфраструктуры (нет vitest/jest, нет
ни одного `*.test.*` файла) — осознанно решено не поднимать её ради этой
задачи. Unit-тесты не пишутся, покрытие — ручная проверка ниже.

**Integration tests:** нет — небольшая фронтенд-правка без новых бэкенд-эндпоинтов
и без изменения схемы данных; риск локализован и покрывается ручной проверкой.

**E2E tests:** нет — задача умеренного размера (Size M, но без новой
инфраструктуры/архитектуры), достаточно ручной проверки на живой панели.

## How to Verify

Живого окружения с MCP-доступом для этой проверки не требуется — все шаги
выполняются вручную в браузере на реальной панели, агентской автоматической
проверки для этой задачи нет.

### User verifies
- Инкремент 1: открыть poshivon.ru/panel → «Настройки» и визуально проверить:
  порядок тарифов поменялся, названия — «Продвинутый»/«Быстрый», надпись
  «Скидки за количество» вместо «Скидки по партиям».
- Инкремент 2: добавить одну новую строку в каждом из 3 блоков (Изделия,
  Усложнения, Скидки за количество) через кнопку «Добавить», заполнив все
  поля формы, нажать «Сохранить изменения», перезагрузить страницу —
  убедиться, что все 3 строки остались и переключение между режимами
  калькулятора не показывает пустых/нулевых полей у новых изделий.
- Удалить одну из добавленных строк кнопкой «Удалить», сохранить,
  перезагрузить — убедиться, что строка пропала.
- Попробовать добавить изделие/усложнение с именем, которое уже есть в
  списке (включая вариант с другим регистром и пробелами по краям) —
  убедиться, что появляется ошибка и дубликат не добавляется.
- Добавить строку в «Скидки за количество» с предложенным по умолчанию
  диапазоном — убедиться, что сохранение проходит без ошибки.
