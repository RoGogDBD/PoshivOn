## Description

This is the shared foundation for Increment 2 (add/delete rows in the
pricing panel's Изделия, Усложнения/Операции, and Скидки за количество
sections). It exists as its own task, before Wave 3's three per-section
tasks (3, 4, 5), specifically so those three tasks — which run in the same
wave and all touch `client/src/pages/Panel.jsx` — never write to the same
lines in parallel: every shared constant, helper, and handler is created
here, once, and Wave 3 tasks only add JSX call-sites against this already
existing code.

The work has two parts: (1) client-side logic (constants, validation,
handlers, a small `DeleteRowButton` component) with no visible UI change yet,
and (2) a targeted `vitest` unit-test carve-out for just this new pure logic
— a deliberate, user-approved deviation from user-spec's original "no unit
tests" decision (tech-spec Decision 7), justified because this project's
Vite config makes `vitest` nearly free to add, and the logic being tested is
the tech-spec's own top-named risk (client-side validation drifting from the
backend's bounds, silently producing bad pricing data — this exact bug class
was found and fixed once already during user-spec review).

## What to do

1. **Default-name constants.** Add two new constants near the existing
   `defaultSettings` object (`client/src/pages/Panel.jsx:96-192`):
   ```js
   const DEFAULT_GARMENT_NAMES = ["Пиджак", "Юбка", "Рубашка", "Платье"];
   const DEFAULT_OPERATION_NAMES = [
     "Карман накладной", "Карман прорезной", "Подклад", "Потайная молния",
     "Воротник", "Манжеты", "Шлица", "Декоративная отстрочка",
   ];
   ```
   These must match `DefaultUserSettings()` in
   `server/internal/service/costing.go:227-242` exactly (4 garments, 8
   operations) — do not derive this list from `defaultSettings` itself (see
   step 2: `defaultSettings.operations` is currently missing 2 of these 8
   names, which is exactly the kind of drift this separate, explicit list is
   meant to avoid repeating).

2. **Fix the stale `defaultSettings.operations`.** `Panel.jsx:118-125`
   currently lists only 6 of the 8 default operations — missing "Шлица" and
   "Декоративная отстрочка". Add them, matching the server exactly:
   ```js
   "Шлица": { additional_minutes: 18, additional_material_per_unit: 50, quick_percent: 7 },
   "Декоративная отстрочка": { additional_minutes: 18, additional_material_per_unit: 0, quick_percent: 5 },
   ```
   (tech-spec Decision 6 — this is a client-only pre-load fallback object,
   zero risk to fix; approved as a user-spec deviation.)

3. **Validation helpers.** Write plain local functions (no library — none
   exists in this project, confirmed: no yup/zod/react-hook-form/formik in
   `client/package.json`):
   - Name-dedup check: given a candidate name and the existing
     `settings.garments` or `settings.operations` object, return whether a
     key already matches after `.trim().toLowerCase()` on both sides.
   - Numeric bound checks mirroring `server/internal/service/costing.go`'s
     `validateSettings` (lines 616-654) — but **equal or stricter**, per
     tech-spec AC:
     - Garment: `quick_price > 0` (backend's save-time check only requires
       `>= 0`, but the quick-mode price calculation at `costing.go:720-721`
       throws if `quick_price <= 0` — client must reject `0` to avoid ever
       producing that state), `base_minutes > 0`, `complexity_coeff > 0`.
     - Operation: `additional_minutes >= 0`, `additional_material_per_unit
       >= 0`, `quick_percent >= 0`.
     - Discount: `min_qty > 0`, `max_qty >= min_qty`,
       `0 <= percent <= 100`.
   - Do NOT reuse the existing `Number(value) || 0` coercion pattern used by
     `handleGarmentChange` etc. (`Panel.jsx:479+`) — it silently turns
     invalid/empty input into `0`, which is exactly the value these checks
     must reject. Use explicit `Number.isFinite(n) && n > 0` (or `>= 0`)
     style checks.

4. **`getDefaultDiscountRange(existingTiers)` helper.** Computes **both**
   ends of a suggested new discount tier — not just `min_qty`:
   ```js
   const getDefaultDiscountRange = (existingTiers) => {
     const lastTier = existingTiers[existingTiers.length - 1];
     const minQty = lastTier ? lastTier.max_qty + 1 : 1;
     return { min_qty: minQty, max_qty: minQty };
   };
   ```
   (Dropping the `max_qty` default here was a critical gap caught during
   tech-spec validation — user-spec's AC explicitly requires both ends
   pre-filled, so a fresh add-form never defaults to an invalid/blank range
   that would block the whole settings save.)

5. **Six new handlers**, added alongside the existing
   `handleGarmentChange`/`handleOperationSettingChange`/`handleDiscountChange`
   block (`Panel.jsx:479-548`), following their exact
   `setSettings((current) => ({ ...current, <key>: <new value> }))`
   immutable-update style (read `handleGarmentChange` at line 479 and
   `handleDiscountChange` at line 518 first, to match the pattern precisely):
   - `handleAddGarment(name, fields)` — adds `{ [name]: fields }` to
     `current.garments`. `fields` is `{ base_minutes, complexity_coeff,
     quick_price }`, already validated by the caller (Wave 3's add-forms) —
     this handler does not re-validate, it just writes.
   - `handleDeleteGarment(name)` — returns a new `garments` object with
     `name`'s key omitted (e.g. via `Object.fromEntries(Object.entries(...)
     .filter(([key]) => key !== name))` — there's no existing
     delete-a-map-key helper in this file to reuse).
   - `handleAddOperation(name, fields)` / `handleDeleteOperation(name)` —
     same shape, for `current.operations`.
   - `handleAddDiscount(fields)` — appends `fields` to
     `current.batch_discounts` (plain array push, immutable:
     `[...current.batch_discounts, fields]`).
   - `handleDeleteDiscount(index)` — filters out that index:
     `current.batch_discounts.filter((_, i) => i !== index)`.

6. **`DeleteRowButton` component.** Small, renders nothing if not deletable:
   ```js
   const DeleteRowButton = ({ isDeletable, onDelete }) =>
     isDeletable ? (
       <button type="button" onClick={onDelete}>Удалить</button>
     ) : null;
   ```
   Style it to read as a secondary/muted action within the existing row-card
   styling (the row container class at e.g. `Panel.jsx:850` is the visual
   context it'll sit inside) — there's no existing theme-aware "danger" color
   token in this project (`client/src/index.css`'s settings token block has
   no `--settings-danger`), so use a plain muted/outline style consistent
   with `settingsInputClass`'s border color rather than inventing a new color
   token for one button.

7. **`vitest` setup.** Add `vitest` as a devDependency to
   `client/package.json` and a `"test": "vitest run"` script. This is a Vite
   project (`client/vite.config.js` already configures `@vitejs/plugin-react`
   + `@tailwindcss/vite`) — `vitest` reuses that config with no changes
   needed; do not add `@testing-library/react` or any other component-testing
   tooling, this carve-out is deliberately narrow (pure-function tests only,
   per tech-spec Decision 7).

8. **Unit test file** (e.g. `client/src/pages/Panel.validation.test.js`)
   covering, at minimum:
   - Name-dedup: exact match, case-different match ("пиджак" vs "Пиджак"),
     whitespace-padded match (" Пиджак ") all flagged as duplicates; a
     genuinely distinct name passes.
   - Each numeric bound's boundary: `0` and negative values rejected where
     `> 0` is required (garment fields); `-0.01`/`-1` rejected where `>= 0`
     is required (operation fields, discount `min_qty`... wait `min_qty`
     needs `> 0` — check each field against the exact rule in step 3, don't
     assume uniformly).
   - `DEFAULT_GARMENT_NAMES` has exactly the 4 names, `DEFAULT_OPERATION_NAMES`
     has exactly the 8 names, matching `server/internal/service/costing.go:227-242`
     verbatim — this is a direct regression guard for the exact drift already
     found once in `defaultSettings.operations` (step 2).
   - `getDefaultDiscountRange`: given a list of tiers, returns `min_qty =
     lastTier.max_qty + 1` AND `max_qty` equal to that same value; given an
     empty list, returns `min_qty = 1, max_qty = 1`.

9. Do not add any JSX call-sites for `GarmentAddForm`/`OperationAddForm`/the
   discount add-form, and do not touch the Изделия/Усложнения/Операции/
   Скидки rendering blocks — that's Wave 3 (Tasks 3, 4, 5), which depend on
   this task and will call the handlers/components created here.
