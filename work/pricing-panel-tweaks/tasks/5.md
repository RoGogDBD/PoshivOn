## Description

This task delivers the "Скидки за количество" (batch-discount tiers) portion
of Increment 2 from user-spec: admins gain the ability to add a new discount
tier and delete an existing one, directly from `client/src/pages/Panel.jsx`.

`DiscountsBlock` (`Panel.jsx:1258`, currently titled "Скидки по партиям" —
Task 1 renames the title separately) is already a **single shared component**
called identically from both calculator-mode branches (`Panel.jsx:885` inside
the quick-mode branch, `Panel.jsx:966` inside the masterpiece-mode branch,
both passing the same `settings`/`handleDiscountChange` props). Unlike
Изделия/Усложнения (Tasks 3/4), there is no per-mode duplication to handle
here and no extraction needed — everything for this task lives inside this
one component definition.

Task 2 (dependency) adds the shared foundation this task consumes: the
`getDefaultDiscountRange(existingTiers)` helper, the `handleAddDiscount` and
`handleDeleteDiscount` handlers (added to the existing handlers block around
`Panel.jsx:479-548`, following the same `setSettings((current) => ({...}))`
immutable-update style as `handleDiscountChange` at `Panel.jsx:518-525`), and
the `DeleteRowButton` component. **Do not re-implement or modify any of
these** — this task only adds JSX call-sites inside `DiscountsBlock` that
invoke them. If Task 2's code isn't present yet in `Panel.jsx` when this task
starts, stop and flag it — this task cannot proceed without it (that's the
`depends_on: [2]` dependency).

Two behaviors this task must get exactly right, both called out explicitly in
tech-spec (Architecture, Decision 3) and user-spec (Constraints):

1. **Default range pre-fill covers both ends.** `getDefaultDiscountRange`
   returns an object with **both** `min_qty = lastTier.max_qty + 1` **and**
   `max_qty` set to that *same* value (not left blank or zero). A form that
   only pre-fills `min_qty` and leaves `max_qty` empty/0 would fail backend
   validation (`MaxQty >= MinQty` is fine at equal values, but a blank/0
   `max_qty` is not) and reintroduce the exact "invalid new row blocks the
   whole save" bug user-spec spent three revision rounds closing — because
   save is a single whole-object `POST`, one bad new tier blocks *all*
   unrelated edits in the same session too.
2. **The last remaining tier can never be deleted.** `server`'s
   `normalizeSettings` (`server/internal/service/costing.go:659-710`)
   silently replaces an empty `batch_discounts` array with 4 hardcoded
   default tiers on save — so the delete control for the last tier must be
   rendered **disabled**, not simply hidden, and the gate is
   `settings.batch_discounts.length > 1` (i.e. more than one tier currently
   exists) before allowing that row's delete to fire.

**Files:**
- `client/src/pages/Panel.jsx` — `DiscountsBlock` component only (currently `Panel.jsx:1258-1282`; confirm exact current line range at task start, since Tasks 1-4 may have shifted it). Add the inline add-form and wire `DeleteRowButton` into the existing row `.map(...)`. Do not touch the component's call sites at `Panel.jsx:885`/`966` (they need no changes), the Изделия/Усложнения sections (Tasks 3/4), or any of Task 2's shared code (constants, handlers, `getDefaultDiscountRange`, `DeleteRowButton` definition).

**Dependencies:**
- Task 2 (foundation: `getDefaultDiscountRange`, `handleAddDiscount`, `handleDeleteDiscount`, `DeleteRowButton`) — hard prerequisite, must be present in `Panel.jsx` before this task starts.

**Edge cases:**
- Server-side default tiers (`server/internal/service/costing.go:305-309`) end with `{MinQty: 101, MaxQty: 1000000, Percent: 12}` — on a freshly-loaded default settings object, `getDefaultDiscountRange` would compute a degenerate `1000001–1000001` range. This is expected/accepted per user-spec Constraints ("осознанно допустимо") — the pre-filled range is a valid starting point the admin is expected to edit, not a recommendation. Do not special-case this in the add-form.
- Deleting a middle tier can leave a coverage "hole" (e.g. 1-10 / 11-50 / 51-100 → delete 11-50 → quantities 11-50 get no discount). This is an accepted, out-of-scope limitation per user-spec Constraints and tech-spec Risks — no continuity check is required.
- The last-tier delete gate must disable the control, not hide it — an admin should be able to see why they can't delete (vs. the control silently vanishing).
- `batch_discounts` array key in `settings.batch_discounts.map((discount, index) => ...)` currently uses `key={\`${discount.min_qty}-${discount.max_qty}-${index}\`}` (`Panel.jsx:1267`) — keep this key scheme intact when adding the delete button into the same row markup.

**Implementation hints:**
- Match the existing row's field styling/order exactly: `SettingsField label="От"` → `min_qty`, `SettingsField label="До"` → `max_qty`, `SettingsField label="Скидка, %"` → `percent` (`Panel.jsx:1269-1277`). The add-form's fields should read the same way so the form doesn't look like a foreign element bolted onto the section.
- The add-form needs its own local state for the three input values (it's not one of the existing per-tier rows), initialized from `getDefaultDiscountRange(settings.batch_discounts)` — recompute the default whenever the tier list changes (e.g. after an add), so the form always suggests picking up where the current last tier leaves off.
- Match `settingsInputClass`/`SettingsNumberInput` numeric attributes already used for these three fields (`min="1"` for мин/макс, `step="0.01" min="0" max="100"` for процент) so the browser-level constraints stay consistent with the existing rows.
