## Description

This is the Security Audit task from the tech-spec's Audit Wave — the third of
three parallel full-feature audits (alongside Task 6 Code Audit and Task 8
Test Audit), run after all Increment 2 implementation (Tasks 3, 4, 5) is
complete. It is a security-analysis task, not a code-writing task: this
task's own output *is* the review, so `reviewers` is intentionally empty and
there is no TDD anchor.

`pricing-panel-tweaks` adds no new backend endpoints, no schema changes, and
no new auth/access-control surface — everything lives in one client file,
`client/src/pages/Panel.jsx` (React/Vite), with persistence riding the
existing `handleSaveSettings` → `POST /api/v1/users/settings` whole-object
save flow. Given that, the audit's center of gravity is client-side: does
free-text admin input (garment/operation names, typed via the three new
add-forms from Tasks 3/4/5) get handled safely everywhere it flows —
in the React UI itself, and in the one already-known downstream consumer,
the AI market-feedback prompt on the backend.

Tech-spec's Risks table already documents one accepted, pre-existing item
that this audit must re-confirm rather than re-litigate: garment/operation
names flow unescaped into the AI market-feedback prompt built in
`server/internal/service/deepseek.go` (string-interpolated via
`strings.Join(sortedKeysFromGarments(settings.Garments), ", ")` at line 404,
alongside the analogous `Materials`/`Urgency` joins at lines 405-406). This is
pre-existing backend behavior — names were never content-restricted there —
and is explicitly out of scope to fix in this feature. What *is* new is that
this feature makes that same input reachable via a discoverable UI action
(the "Добавить" forms) instead of only a hand-crafted API call. The job here
is to confirm the trust boundary and blast radius assessment in the Risks
table still holds after Tasks 3/4/5 landed — not to propose fixing
`deepseek.go`.

## What to do

- Read every source file created or modified across this feature's
  implementation waves (per tech-spec "Files to modify" and this feature's
  `decisions.md` entries for Tasks 1-5): `client/src/pages/Panel.jsx` (the
  full diff — `calculatorModes`/`DiscountsBlock` edits, the new constants/
  validation helpers/handlers from Task 2, and the three add-form/
  delete-button call sites from Tasks 3/4/5), the new `client/src/pages/
  Panel.validation.test.js` test file, and `client/package.json`'s `vitest`
  devDependency addition.
- Analyze against OWASP Top 10, scoped to what this feature actually touches
  (no new backend endpoints exist, so authentication/session/access-control
  analysis is a confirmation that nothing changed there, not a fresh audit of
  `/panel` auth):
  - **XSS (client-side):** confirm every place a user-typed garment/operation
    name or numeric field is rendered back into the DOM goes through normal
    JSX interpolation (auto-escaped) and that no `dangerouslySetInnerHTML`,
    raw `innerHTML` assignment, or equivalent was introduced anywhere in the
    new components (`GarmentAddForm`, `OperationAddForm`, the discount
    inline add-form, `DeleteRowButton`) or their call sites.
  - **Input validation consistency:** compare the client-side validation in
    each of the three add-forms (Tasks 3/4/5) against Task 2's shared
    validation helpers (name-dedup check, numeric bound checks) and against
    backend `validateSettings` (`server/internal/service/costing.go:593`) —
    confirm client bounds are equal-or-stricter everywhere, matching
    tech-spec's own Acceptance Criteria, and that no add-form bypasses or
    duplicates-with-drift the shared helpers.
  - **Injection / secrets:** confirm no SQL/command construction was touched
    (none should be — no backend files are modified by this feature) and no
    hardcoded secrets, tokens, or credentials were introduced anywhere in the
    diff.
  - **Re-confirm the known accepted risk:** re-read
    `server/internal/service/deepseek.go` (around lines 400-410, the prompt
    template's `%s` substitutions built from `sortedKeysFromGarments`/
    `sortedKeysFromMaterials`/`sortedKeysFromUrgency`) and confirm: (a) this
    backend file is genuinely untouched by this feature, (b) the blast radius
    is still self-scoped to the same authenticated user's own AI feedback
    request (no cross-user exposure), and (c) the new add-forms don't
    introduce any additional unescaped sink beyond this already-documented
    one.
- Classify any findings by severity (Critical/High/Medium/Low) per the
  security-auditor skill's methodology, with file:line references, attack
  vector, and impact for each.
- Write the audit report to
  `work/pricing-panel-tweaks/logs/working/task-7/security-audit-report.md`,
  including: scope of files reviewed, findings by severity (or "no findings"
  per category), and an explicit re-confirmation statement for the
  `deepseek.go` accepted-risk item (still holds / no longer holds — with
  reasoning either way).
- If any Critical or High findings are discovered, flag them clearly at the
  top of the report — this feature has no fixer step built into the Audit
  Wave, so such findings need to be surfaced prominently for the orchestrator
  to act on rather than buried in a findings list.

## Details

**Files:**
- `client/src/pages/Panel.jsx` — primary audit target, the entire feature's
  diff lives here (Tasks 1-5 all modify only this file).
- `client/src/pages/Panel.validation.test.js` — new test file; check it
  doesn't hardcode or leak anything sensitive, and isn't itself a code-injection
  vector (it isn't — it's local unit tests — but confirm).
- `client/package.json` — confirm only `vitest` was added as a devDependency,
  no unexpected/unpinned/suspicious package.
- `server/internal/service/deepseek.go:400-410` — read-only reference, not
  modified by this feature; used to re-confirm the accepted Risks-table item.
- `server/internal/service/costing.go:593` (`validateSettings`), `:659`
  (`normalizeSettings`) — read-only reference for comparing client-side
  validation bounds.

**Dependencies:** depends on Tasks 3, 4, 5 (all three Increment 2 add/delete
tasks) being complete, since this audit covers the full add-form surface.
Runs in parallel with Task 6 (Code Audit) and Task 8 (Test Audit) — same
wave, independent of each other.

**Edge cases:**
- A finding that only manifests in one of the two calculator-mode render
  sites (quick vs. masterpiece) for the same component — check both, per
  tech-spec Decision 5's twice-rendered pattern.
- Validation drift that is *stricter* on the client than the backend is not a
  security issue (backend still enforces its own bounds) — only client bounds
  *looser* than backend bounds are a finding, since those let an
  invalid-but-client-accepted value reach the backend save call (which will
  then reject it, but worth noting if the UX silently produces a confusing
  save failure).
- Do not re-open Decision 3's accepted design (defaults are never deletable)
  or the deliberately-accepted discount-tier-gap / deleted-item-in-saved-calc
  risks already documented in tech-spec's Risks table as conscious,
  user-approved decisions — those are out of scope to re-litigate here,
  only the `deepseek.go` item needs explicit re-confirmation.

**Implementation hints:** use `git log --oneline -- client/src/pages/Panel.jsx`
and this feature's `decisions.md` to identify exactly which commits/lines
belong to this feature versus pre-existing code, so the audit doesn't flag
pre-existing patterns as new findings.
