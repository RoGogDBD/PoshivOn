## Description

This is Wave 3 of the `pricing-panel-tweaks` Increment 2 rollout: the ability to
add and delete rows in the Усложнения/Операции ("complications"/"operations")
block of the pricing panel settings form (`client/src/pages/Panel.jsx`), one of
three sibling blocks getting the same add/delete treatment (Изделия is Task 3,
Скидки за количество is Task 5 — both run in this same wave, on disjoint
sections of the same file).

The shared foundation (constants, validation helpers, handlers, `DeleteRowButton`)
is built by Task 2, which this task depends on. Task 2 adds — among other things
— `DEFAULT_OPERATION_NAMES` (the 8 hardcoded default operation names, cross-checked
against `server/internal/service/costing.go:233-242`), a numeric-bounds validator
for operation fields, a name-dedup check, `handleAddOperation`/`handleDeleteOperation`
(following the existing `setSettings((current) => ({...}))` immutable-update
style used by `handleOperationSettingChange` at `Panel.jsx:492-503`), and the
`DeleteRowButton` component itself. This task only adds JSX call-sites in the
Усложнения/Операции sections — it must not touch Task 2's shared code, and must
not touch the Изделия sections (Task 3) or `DiscountsBlock` (Task 5).

The panel renders two structurally different views of the same
`settings.operations` map depending on `calculatorMode` (`isQuickCalculator`
branch at `Panel.jsx:845-886` vs. the masterpiece branch at `Panel.jsx:887-1003`)
— quick mode's block is titled "Усложнения" (`Panel.jsx:866-883`, one field:
`quick_percent`), masterpiece mode's is titled "Операции" (`Panel.jsx:925-945`,
two fields: `additional_minutes`, `additional_material_per_unit`). Per tech-spec
Decision 2, the new `OperationAddForm` collects **all four** operation fields
(Название, Надбавка %, Доп. минуты, Доп. материал/шт) in both places — never a
subset conditioned on which mode is active — so a row added while in one mode
can never end up with a hidden/missing field that silently breaks the other
mode's calculation later. Per Decision 5, `OperationAddForm` is defined once and
rendered at both sites, mirroring the one existing precedent in this file for
that pattern: `DiscountsBlock` (`Panel.jsx:1258-1282`), already invoked
identically from both mode branches (`Panel.jsx:885` and `Panel.jsx:966`).

## What to do

- Build `OperationAddForm`, a new small component (defined once, near
  `DeleteRowButton`/other new Task 2 components, or directly above the `Panel`
  component alongside `DiscountsBlock` — match whatever placement convention
  Task 2 established for its own new pieces) that:
  - Collects four fields, always all four regardless of `isQuickCalculator`:
    Название (text), Надбавка % (`quick_percent`), Доп. минуты
    (`additional_minutes`), Доп. материал/шт (`additional_material_per_unit`).
  - On submit, runs Task 2's name-dedup check (trimmed, case-insensitive,
    against `Object.keys(settings.operations)`) and Task 2's numeric-bounds
    check for operation fields (all three numeric fields `>= 0`, matching
    backend `validateSettings` at `server/internal/service/costing.go:634-644`).
  - On validation failure, shows an inline error (dedup: "Такое название уже
    есть"; bounds: reject negative values) and does not call the handler.
  - On success, calls Task 2's `handleAddOperation(name, fields)` and resets
    its own local form state (so the fields are empty for the next add, not
    left showing the just-added values).
  - Uses the existing `SettingsField`/`SettingsNumberInput`/`settingsInputClass`
    conventions (`Panel.jsx:207-238`) for visual consistency with the rest of
    the form — no new input styling.
- Render one `OperationAddForm` inside the quick-mode "Усложнения"
  `SettingsSection` (currently `Panel.jsx:866-883`), after the existing
  `.map(...)` row list, inside the same `SettingsSection`.
- Render one `OperationAddForm` inside the masterpiece-mode "Операции"
  `SettingsSection` (currently `Panel.jsx:925-945`), after its existing
  `.map(...)` row list, inside the same `SettingsSection`.
- In both existing per-row `.map(...)` blocks (the one at `Panel.jsx:868-881`
  for quick mode, the one at `Panel.jsx:927-943` for masterpiece mode), render
  Task 2's `DeleteRowButton` next to each row, computing
  `isDeletable={!DEFAULT_OPERATION_NAMES.includes(name)}` and wiring its click
  to Task 2's `handleDeleteOperation(name)`.
- Confirm both insertion points end up wired to the exact same
  `settings.operations` state (shared, not per-mode) — an add or delete in one
  mode must be immediately visible after switching to the other mode, since
  both branches map over the same `settings.operations` object.
- Do not modify Task 2's constants/handlers/helpers/`DeleteRowButton`
  definitions, the Изделия `SettingsSection` blocks, or `DiscountsBlock` — read
  them, call them, don't change them.

## Acceptance Criteria

- [ ] Exactly one "Добавить" control for Усложнения/Операции is visible at any time — inside whichever of the two `SettingsSection` blocks (quick "Усложнения" or masterpiece "Операции") is currently rendered.
- [ ] `OperationAddForm` always shows all four fields (Название, Надбавка %, Доп. минуты, Доп. материал/шт) in both calculator modes — no field is hidden or defaulted based on `isQuickCalculator`.
- [ ] Submitting the add-form with a negative value in Надбавка %, Доп. минуты, or Доп. материал/шт is rejected client-side (no `handleAddOperation` call, no row added).
- [ ] Submitting the add-form with a name that already exists in `settings.operations` (case-insensitive, trimmed) is rejected with a "Такое название уже есть"-type error, no duplicate row added.
- [ ] A valid submission calls `handleAddOperation`, the new row appears immediately in both calculator modes (shared `settings.operations` state), and after "Сохранить изменения" + reload it persists.
- [ ] `DeleteRowButton` renders and works for a row whose name is not in `DEFAULT_OPERATION_NAMES`; it does not render (or renders disabled/absent per Task 2's `DeleteRowButton` contract) for all 8 default operation names, in both calculator modes.
- [ ] Deleting an admin-added row via `handleDeleteOperation` + "Сохранить изменения" + reload removes it permanently (does not reappear).
- [ ] No changes made to the Изделия `SettingsSection` blocks or `DiscountsBlock` in this task's diff.

**Edge cases:**
- A name that duplicates an existing *garment* name (not operation) is fine — dedup is scoped to `settings.operations` only, not cross-checked against `settings.garments`.
- Whitespace-only or empty Название must be rejected (empty-name check is part of Task 2's validation helpers, not something to reimplement here — just make sure the form calls it before submit).
- `0` is a valid value for all three operation numeric fields (bounds are `>= 0`, not `> 0` — unlike garments in Task 3, where `0` is rejected). Do not accidentally reuse Task 3's garment bound logic for operations.
- After a successful add, the form must clear back to empty so the admin isn't confused into re-submitting the same values as a second row.
- Switching calculator mode after adding/deleting (before saving) must show the same up-to-date row list in both modes, since both branches read the same `settings.operations` state — no separate per-mode copy.

**Implementation hints:**
- Match the existing per-row wrapper markup style (`grid gap-4 rounded-[24px] border p-4 ... key={name}`) used at `Panel.jsx:869-872` and `Panel.jsx:928-931` when adding the delete button inside each row — don't introduce a new row-wrapper pattern.
- `OperationAddForm` needs its own local `useState` for the four draft field values and an error-message string; it is not lifted into `settings` until a successful submit.
