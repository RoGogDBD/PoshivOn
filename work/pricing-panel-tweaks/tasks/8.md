## Description

Full-feature test quality audit for `pricing-panel-tweaks` (Audit Wave, tech-spec
"Task N: Test Audit"). This is not a code-writing task — the auditor's review
*is* the deliverable, there is no separate reviewer round.

Tech-spec Decision 7 deliberately narrowed this feature's test coverage: a
targeted `vitest` unit-test file covers only the new *pure validation logic*
in `client/src/pages/Panel.jsx` (name-dedup check, per-field numeric bound
checks, the `DEFAULT_GARMENT_NAMES`/`DEFAULT_OPERATION_NAMES` constants, and
`getDefaultDiscountRange`). Explicitly out of that file's scope, by the same
decision and by Testing Strategy: any React component/DOM testing of
`GarmentAddForm`, `OperationAddForm`, and `DeleteRowButton` — that surface is
covered only by the manual verification checklist (user-spec "How to Verify"
plus each Wave 3 task's `Verify-user` field).

This audit has two jobs, matching that split:
1. Verify the unit tests actually deliver on Decision 7's promise — every
   documented bound and both default-name lists are genuinely exercised, and
   no assertion is trivial/tautological (e.g. asserting a constant equals
   itself, or a function returns what it's hardcoded to return without
   exercising real branching logic).
2. Verify the *deliberately untested* surface (the three components built in
   Tasks 3/4/5) is genuinely adequately covered by the manual checklist — not
   just that a checklist exists, but that it actually walks through
   client-side rejection of every out-of-bounds value, both render sites per
   component (quick and masterpiece mode), delete-button visibility/absence
   for default vs. admin-added rows, and persistence-after-reload for both
   add and delete.

This is this feature's top-named risk (tech-spec Risks table, row 3):
client-side validation drifting from backend `validateSettings` bounds is
exactly the bug class (`quick_price = 0` reaching production) that took a
full round of user-spec revision to catch by inspection alone. Decision 7
converts that from a one-time authorship check into a permanent regression
guard — this audit is what confirms the guard actually holds, and that the
untested remainder isn't quietly under-covered too.

## Details

**Files (read-only for this task — audit does not modify code):**
- `client/src/pages/Panel.jsx` — read the constants/helpers/handlers from Task 2 and the component code from Tasks 3/4/5.
- new test file from Task 2 (exact filename to confirm on read) — read every test case and cross-check against the bounds above.
- `server/internal/service/costing.go:227-242, 593-654` — source of truth for both default-name lists and every numeric bound; the test file's assertions must be checked against this file, not against the test file's own comments or the tech-spec's paraphrase of it.

**Dependencies:** Tasks 3, 4, 5 (all three Wave 3 components must exist so the manual-checklist-adequacy half of this audit has real `Verify-user` fields to assess); the test file itself comes from Task 2, which is not a direct dependency per the tech-spec's task graph but must already exist for this audit to run.

**Edge cases to specifically check for in the test file:**
- Operation fields are `>= 0` (0 must be a *passing* case) — a common test-writing mistake is to treat all "numeric bound" fields as `> 0` like the garment fields, silently failing to test that operation `0` is valid.
- Discount `max_qty >= min_qty` allows equality — confirm a test exists for `max_qty === min_qty` passing, not just `max_qty < min_qty` rejecting.
- Discount `percent` boundaries at exactly `0` and exactly `100` must pass, not just values strictly inside the range.
- `DEFAULT_OPERATION_NAMES` must include "Шлица" and "Декоративная отстрочка" — these are the two names Decision 6 found missing from the pre-existing `defaultSettings.operations`; a test that only checks a subset or checks length-8 without checking exact names could pass with the wrong 8 names.

**Implementation hints:** This is a reading-and-judgment task, not an
implementation task — there is no code to write. Treat "trivial/tautological"
strictly: a legitimate boundary-value assertion (e.g. `expect(isValidQuickPrice(0)).toBe(false)`)
is not trivial even though it looks simple; a test is trivial only if it
can't fail given a wrong implementation (e.g. asserting a hardcoded array
literal equals itself instead of calling the actual exported constant).
