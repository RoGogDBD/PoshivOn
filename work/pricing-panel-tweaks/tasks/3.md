## Description

The admin pricing panel (`client/src/pages/Panel.jsx`) currently renders the
Изделия (garments) list in two places — once inside the quick-calculator
branch (`isQuickCalculator ? (...) : (...)`) showing only `Мин. цена / шт`,
and once inside the masterpiece branch showing `База, мин` + `Коэфф.` — but
has no way to add a new garment or remove one from the UI. This task adds
that capability: one "Добавить" button per Изделия section (present in both
branches, not duplicated per mode), collecting **all** garment fields at once
regardless of which mode is active (per tech-spec Decision 2 — this
eliminates the class of bug where a garment added in one mode gets a
zero/missing value for a field only shown in the other mode), plus an
"Удалить" control on rows the admin added themselves.

This task depends on Task 2, which already created `handleAddGarment`,
`handleDeleteGarment`, the validation helpers (name-dedup, numeric bounds),
`DEFAULT_GARMENT_NAMES`, and `DeleteRowButton`. This task only builds the
`GarmentAddForm` component and wires it + `DeleteRowButton` into the existing
JSX — it does not touch handlers, constants, or validation logic.

## Acceptance Criteria

- [ ] Exactly one "Добавить" button is visible for Изделия regardless of
      which calculator mode (Быстрый/Продвинутый) is currently active — not
      duplicated or missing in either mode.
- [ ] The add-form always shows all 4 fields (Название, Мин. цена/шт, База/мин,
      Коэфф. сложности) in both modes — no field is hidden or defaulted based
      on the active mode.
- [ ] Submitting the form with `Мин. цена/шт <= 0`, `База/мин <= 0`, or
      `Коэфф. сложности <= 0` is rejected client-side with a visible error;
      the row is not added.
- [ ] Submitting the form with a name matching an existing garment
      (case-insensitive, ignoring leading/trailing whitespace) is rejected
      with a visible "Такое название уже есть" error; the existing row is not
      overwritten.
- [ ] A successfully added garment appears immediately in both calculator
      modes' Изделия lists (same underlying `settings.garments` object).
- [ ] "Удалить" is visible and functional on a garment added through this
      form; "Удалить" is absent for all 4 default garments (Пиджак, Юбка,
      Рубашка, Платье) in both modes.
- [ ] Deleting an added garment removes it from both mode views immediately;
      after clicking "Сохранить изменения" and reloading the page, the
      deletion persists.
- [ ] Adding then saving a garment, then switching calculator mode and
      recalculating a price for it, produces a correct result in both modes
      (no `NaN`, no thrown error) — confirms all 3 numeric fields were
      genuinely captured, not defaulted.

## Details

**Files:**
- `client/src/pages/Panel.jsx` — add `GarmentAddForm` component; insert one
  call in each of the two Изделия `SettingsSection` blocks (~847-864 quick,
  ~903-923 masterpiece); add `DeleteRowButton` to each Изделия row
  (~850-861 quick, ~906-920 masterpiece).

**Dependencies:** Task 2 (must be complete — this task calls
`handleAddGarment`, `handleDeleteGarment`, `DEFAULT_GARMENT_NAMES`,
`DeleteRowButton`, and the validation helpers it defines).

**Edge cases:**
- A row added in quick mode must show correct values when viewed in
  masterpiece mode and vice versa — both modes render the same
  `settings.garments` object, so this should be automatic if the add-form
  genuinely captures all 4 fields; verify it explicitly rather than assuming.
- Name comparison for the dedup check must trim whitespace and ignore case —
  reuse Task 2's helper rather than writing a second comparison here.

**Implementation hints:**
- Match the existing row-container class string exactly when styling
  `GarmentAddForm`'s fields, so it reads as part of the same list visually —
  see the class string on the row `<div>` at line 850/905 for reference (a
  card style: `rounded-[24px] border p-4 [background:color-mix(...)]`, etc.).
  The add-form doesn't need to be an identical row, but should feel native to
  the section (e.g. a lighter/dashed-border variant, or a simple inline row of
  inputs + button — implementer's visual judgment, no exact mock provided).
- `Number(value) || 0` (the existing coercion pattern used in
  `handleGarmentChange` etc.) is explicitly NOT suitable for this form's
  validation — it silently turns invalid/empty input into `0`, which is
  exactly the value this task must reject. Use `Number.isFinite(n) && n > 0`
  style checks instead (per Task 2's validation helpers).
